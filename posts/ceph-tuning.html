1先建立心智模型：Ceph 性能由什么决定

关于"Ceph 慢"，最常见的误解是把它当成单一黑盒。实际上 Ceph 的性能是一个串联链路，最终耗时由链条上最慢的那一环决定 —— 而不是平均值。这意味着：把最快的那环优化 10 倍，性能一点都不会变。

🔑 定律一：短板决定

非瓶颈环节的优化收益≈0。先测后调。

🔑 定律二：复制放大

1 次客户端写 = 3 次磁盘写 + 2 次跨网络写。后端网流量 ≈ 前端 2 倍（3 副本）。

🔑 定律三：随机惩罚

机械盘随机 IOPS 只有顺序的 1/100。Ceph 的写放大让随机写代价被进一步放大。

1.1 Ceph 相对裸盘的性能折扣（先建立合理预期）

场景相对裸盘原因与说明
3 副本随机小写（4K）约 1/3 ~ 1/53 份写入 + 网络往返 + WAL + 元数据；HDD 上尤其惨
3 副本大块顺序写（1M+）约 1/3 ~ 1/4主要受限于网络与磁盘带宽，放大倍数 ≈ 副本数
3 副本大块顺序读接近 1/3 ~ 1/2只读主副本，但仍是 1 份数据流；实际可接近单盘带宽
EC 4+2 大块写约 1/1.5（容量视角）写放大 1.5x 而非 3x，但计算开销增加、小写有读改写惩罚
全闪 NVMe 集群软件栈占比可达 50%+介质太快，瓶颈转移到 CPU、网络、锁与队列
合理预期：一块 7200 转 SAS 盘的随机写 IOPS 约 150~200。一个 30 盘 3 副本的 HDD 集群，理论随机写 IOPS ≈ 30×180/3 ≈ 1800 IOPS。如果业务期望"万兆网络 + 30 块盘 = 上万 IOPS"，那不是 Ceph 慢，是选型错了 —— 随机小写场景应该用 SSD/NVMe。

3瓶颈①：磁盘介质与布局

在 80% 的 HDD 集群里，瓶颈就是磁盘本身。这一层没选对，后面所有参数调优都是白费。

3.1 三种典型瓶颈表现与判定

现象判定依据结论与对策
IOPS 上不去，%util 长期 100%iostat -xmt 1：%util≈100、await 远高于 svctm介质 IOPS 到顶。HDD：换 SSD 或加盘数；SSD：检查是否写放大/GC
延迟忽高忽低，偶发 100ms+SMART 的 Current_Pending_Sector>0；dmesg 有 I/O error坏道/慢盘。立即 out 换盘（它正在主导 P99）
带宽打满但 IOPS 很低iostat：w/s 低但 wMB/s 高顺序大块场景，属正常；若期望高 IOPS 需改访问模式
SSD 集群性能越用越差NVMe 写满后 GC 频繁；或 BlueStore db 溢出写放大 + GC。留 OP（过量供给 20%+）；扩 db；定期 trim
 
# 磁盘层排查三板斧
iostat -xmt 1              # 看 %util / await / r_await / w_await / aqu-sz
#   %util=100 且 aqu-sz(队列深度) > 4 → 磁盘已饱和
#   await >> svctm → 请求在排队，磁盘是瓶颈
#   w_await 明显高于 r_await → 写缓存/写放大问题

smartctl -a /dev/sdX | grep -Ei 'reallocated|pending|offline|uncorrectable|wear'

3.2 写放大：为什么"写 4K 实际写了几十 K"

3.3 db / wal 布局的三种方案与容量配比

方案 A：单盘（不分离）

所有内容一块盘。
适用：全闪 NVMe 集群（介质本身够快，分离收益小且增加复杂度）。
风险：RocksDB compaction 与数据写竞争。

方案 B：wal+db 共用 NVMe ★

最常见。--block.db /dev/nvme0n1。
适用：HDD 集群 / SATA SSD 集群。
配比：db = 主盘容量 × 4%（HDD）；NVMe 主盘 2%~4%。最小 30GB。

方案 C：wal / db 三分

wal 放最快（Optane/高端 NVMe），db 放普通 NVMe。
适用：极致低延迟要求。
配比：wal 2~10GB 即可。

# 一块 NVMe 能承载几个 OSD 的 db？（经验值，企业级 NVMe，带掉电保护）
#   HDD 主盘：db 按容量 4% 计算 → 3.84T NVMe 可承载约 20~24 个 4TB HDD 的 db(160G each)
#   实践中建议 不超过 8~10 个 OSD/NVMe：因为 NVMe 的 IOPS 和带宽会被多个 OSD 的
#   RocksDB compaction 争抢，且一块 NVMe 故障会同时影响所有依赖它的 OSD（★ 故障域！）

# 推荐布局：2 块 NVMe 做 RAID1（或 2 个独立 NVMe 各承载一半 OSD），避免单点
# 创建示例
ceph-volume lvm create --data /dev/sdd --block.db /dev/nvme0n1   # 自动分配
ceph-volume lvm create --data /dev/sdd --block.db vg_nvme/lv_db5 --block.db-size 160G

# 查看与验证
ceph-volume lvm list
ceph osd metadata 12 | jq '.bluefs, .bluestore_bdev_dev_node, .objectstore'
db 溢出（spillover）—— 全闪/混闪集群性能衰减的头号原因：当 db 空间不足，RocksDB 会把部分元数据写到慢的主设备上，性能断崖式下跌。
检测：ceph tell osd.N perf dump | jq '.bluestore | with_entries(select(.key|test("spillover|bluefs")))'
临时缓解：ceph tell osd.N compact（触发 RocksDB 压缩，回收空间）
根治：扩容 db LV，或按 4% 重建 OSD。预防：部署时就按 4% 分配，不要省这点空间。

4瓶颈②：网络（第二常见的瓶颈）

Ceph 是网络密集型系统。3 副本下，客户端写 1 份数据，网络要传输 3 份（1 进 + 2 出）。网络一旦成为瓶颈，表现是"所有 OSD 一起慢"，很容易和数据面问题混淆。

4.1 前端网 / 后端网流量模型

4.2 网络瓶颈的判定与常见根因

# 判定三件套
sar -n DEV 1                       # 看网卡带宽利用率（%ifutil，RHEL7+）
ethtool -S eth0 | grep -Ei 'err|drop|discard|timeout|crc'   # ★ 错误包是硬指标
ip -s link show eth0               # RX/TX dropped / errors
ceph daemon osd.N dump_osd_network <timestamp>   # ★ Ceph 自带的 OSD 间延迟矩阵

# PPS 瓶颈（容易被忽略）：小包场景先打满的是 PPS 而非带宽
sar -n DEV 1 | awk '{print $2, $3, $4}'    # rxpck/s + txpck/s
# 万兆网卡小包上限约 1.2 Mpps；64 字节包时带宽只用了 ~780 Mbps 但 PPS 已到顶
根因现象对策
前后端网未分离recovery / backfill 时业务 IO 全崩必须物理分离（不同网段/网卡/交换机）
带宽不足顺序读写跑不满磁盘聚合带宽升级到 25/100 GbE，或 bond（LACP）
MTU 不一致 / 巨帧未开大块传输吞吐低、CPU 软中断高全网统一 MTU 9000（包括交换机），用 ping -M do -s 8972 验证
丢包 / CRC 错误延迟抖动大、slow ops 随机分布换光模块/线缆/端口；检查交换机 buffer 与拥塞
软中断集中单核单核 100%（si 高），整体带宽上不去开 RSS / RPS / XPS，多队列网卡绑中断（irqbalance 或手工 smp_affinity）
TCP 参数保守长肥管道（高带宽高延迟）下吞吐不足调大 net.core.rmem/wmem_max、net.ipv4.tcp_rmem/wmem
 
# 网络相关内核参数（/etc/sysctl.d/99-ceph.conf）
net.core.rmem_max = 56623104
net.core.wmem_max = 56623104
net.core.rmem_default = 56623104
net.core.wmem_default = 56623104
net.core.netdev_max_backlog = 250000
net.core.somaxconn = 65535
net.ipv4.tcp_rmem = 4096 87380 56623104
net.ipv4.tcp_wmem = 4096 65536 56623104
net.ipv4.tcp_window_scaling = 1
net.ipv4.tcp_timestamps = 1
net.ipv4.tcp_sack = 1
# 生效：sysctl -p /etc/sysctl.d/99-ceph.conf
进阶：RDMA / msgr v2
全闪集群在 100GbE 下，TCP 协议栈的 CPU 开销会成为瓶颈。可启用 msgr v2（ms_bind_msgr2=true，Squid 起默认开启，支持加密与多连接），进一步可考虑 RDMA（ms_async_rdma）。但注意：RDMA 部署复杂、需要支持 RoCE 的网卡与无损网络配置（PFC/ECN），收益主要在高并发小 IO 场景，HDD 集群完全用不上。

5瓶颈③：CPU（全闪集群的常见瓶颈）

机械盘时代 CPU 很少是瓶颈。但全闪/NVMe 集群里，OSD 进程的单线程瓶颈和单个 CPU 核心的饱和会直接限制 IOPS。

5.1 CPU 的四个消耗大户

① 网络协议栈（messenger）

每个 OSD 有多个 msgr-worker-N 线程负责收发包。全闪集群在 100GbE 下，这部分可能吃掉 30%~50% 的 CPU。表现为软中断（si）高。

② 校验与序列化

CRC32C 校验、消息编解码。可通过 CPU 指令集加速（SSE4.2）。ceph 编译时会检测；ceph-osd 日志里能看到是否启用 crc32c 加速。

③ EC 编解码（erasure coding）

EC 写入需要计算校验块，CPU 开销显著。推荐 ISA-L / SIMD 加速插件（ceph osd erasure-code-profile set ... plugin=isa），性能可提升 2~5 倍。

④ 压缩 / 加密

开启 compression_mode=aggressive 或 RGW 服务端加密会显著增加 CPU 消耗。全闪集群慎用压缩（用 CPU 换空间未必划算）。

5.2 判定方法与对策

# 1. 看是不是单核瓶颈（★ 关键：整体 CPU 不高不代表没问题）
top -H -p $(pgrep -d, ceph-osd)      # 按 1 看每核；按 H 看线程
mpstat -P ALL 1                      # 看是否有某核 100%
pidstat -t -p <osd_pid> 1            # 看线程级 CPU

# 常见线程名含义
#   tp_osd_tp        —— OSD 工作线程池（处理 IO 逻辑）
#   msgr-worker-N    —— 网络收发
#   bstore_kv_sync   —— RocksDB / BlueStore 元数据同步（db 慢会体现在这）
#   bstore_aio / bstore_submit —— 磁盘异步 IO 提交
#   safe_timer       —— 定时器
#   osd_srv / heartbeat —— 心跳

# 2. 火焰图定位热点（进阶）
perf record -F 99 -g -p <osd_pid> -- sleep 60
perf script | stackcollapse-perf.pl | flamegraph.pl > osd.svg
现象参数对策硬件对策
tp_osd_tp 线程满调 osd_op_num_threads_per_shard（默认 2，SSD 可 4~8）；osd_op_num_shards（默认 5，SSD 可 10~20）更高主频 CPU
msgr-worker 满 / si 高开 ms_async_op_threads；启用多队列网卡 RSS更多核心；RDMA
EC 写入慢且 CPU 高换 ISA-L 插件；调 ec_k/ec_m 减小计算量支持 AVX2/AVX512 的 CPU
压缩后 IOPS 暴跌改 compression_mode=passive 或关闭或用支持硬件压缩的方案
CPU 选型建议：Ceph OSD 更吃主频和核心数，而非单核极致性能。
• HDD 集群：每 OSD 分配 1~2 核 即可（0.5 核也能跑，但不建议低于 1 核）
• SATA SSD：每 OSD 2~4 核
• NVMe 全闪：每 OSD 4~8 核，且优先高主频（≥2.5GHz）、支持 AVX2/AVX512
• 关闭 CPU 节能（C-State / P-State）：设为 performance 模式，这一项就能带来 10%~30% 的性能提升
# CPU 性能模式（必须做，收益明显且零成本）
cpupower frequency-set -g performance
# 或：for f in /sys/devices/system/cpu/cpu*/cpufreq/scaling_governor; do echo performance > $f; done
# 持久化：GRUB 加 intel_idle.max_cstate=0 processor.max_cstate=1 idle=poll

6瓶颈④：内存

内存不足的表现往往不是"直接挂"，而是性能缓慢下降：RocksDB cache 命中率下降 → 元数据读放大 → 延迟上升。这类问题最容易被误判为"磁盘慢"。

6.1 OSD 内存模型

# 内存相关排查与调参
ceph tell osd.N heap stats                          # TCMalloc 内存分布
ceph tell osd.N perf dump | jq '.rocksdb | with_entries(select(.key|test("cache|hit")))'
#   rocksdb.block.cache.hit  /  .miss  → 计算命中率：hit/(hit+miss)
#   ★ 命中率 < 80% 说明 cache 不足，元数据读会打到磁盘

ceph config get osd.N osd_memory_target            # 查看当前目标（字节）
ceph config set osd osd_memory_target 6442450944   # 设为 6 GB（需重启 OSD 生效）
# 或写入 ceph.conf [osd] 段：osd_memory_target = 6442450944

# 系统层
free -g ; vmstat 1 ; sar -r 1
swapoff -a ; sysctl -w vm.swappiness=1              # ★ OSD 节点必须避免 swap
sysctl -w vm.min_free_kbytes=1048576                # 保留 1G 给内核，避免突发 OOM
swap 是 Ceph 的性能毒药：OSD 一旦开始 swap，延迟会从毫秒级飙到秒级，且往往触发 OOM killer 连锁反应。生产环境建议直接 swapoff -a，并确保内存规划充足。如果必须用 swap，设 vm.swappiness=1（几乎不用）。

7瓶颈⑤：软件栈（BlueStore / WAL / mclock / 节流）

当硬件都到位后，瓶颈往往落在 Ceph 自身的软件设计上。这一层最容易出"隐性天花板" —— 硬件明明很强，性能就是上不去。

7.1 BlueStore 写路径与三个关键开关

7.2 RocksDB compaction：周期性的性能抖动源

# 现象：每隔一段时间（几十分钟到几小时）出现一轮延迟上升，持续几十秒到几分钟
# 原因：RocksDB 后台 compaction 占用 db 设备的 IO 与 CPU

# 1. 确认
ceph tell osd.N perf dump | jq '.rocksdb | with_entries(select(.key|test("compact")))'
#   rocksdb.compact    —— 正在进行的 compaction 数
#   rocksdb.compact_queue_len —— 队列长度（>0 说明积压）
#   rocksdb.stall      —— ★ 出现 stall 说明 compaction 完全跟不上，写入被暂停

# 2. 缓解参数
ceph tell osd.* injectargs '--bluestore_rocksdb_options=compression=kNoCompression,\
max_write_buffer_number=16,\
min_write_buffer_number_to_merge=3,\
recycle_log_file_num=16,\
level0_file_num_compaction_trigger=6,\
max_bytes_for_level_base=4GB,\
max_bytes_for_level_multiplier=8'

# 3. 手动触发压缩（回收空间、整理 LSM）
ceph tell osd.N compact

# 4. 应急：临时降低 compaction 压力（把 db 压力让给业务）
ceph tell osd.N injectargs '--bluestore_rocksdb_options=disable_auto_compactions=true'
# ★ 用完必须改回 false，否则 LSM 无限增长最终撑爆 db
关于关闭 compression：RocksDB 默认开启 Snappy 压缩。全闪集群为了省 CPU 可以关闭（compression=kNoCompression），代价是 db 空间占用增大约 30%~50%。建议：HDD 保留压缩（省 IO），NVMe 关闭压缩（省 CPU）。

7.3 节流（throttle）：为什么"跑一会儿就变慢"

BlueStore 有一套自适应节流机制：当异步落盘跟不上写入速度时，会主动延迟前台请求（sleep），保护自身不被压垮。表现是压测刚开始很快，几分钟后掉到一半 —— 这不是 bug，是保护机制在起作用。

# 关键节流参数
bluestore_throttle_bytes          # 延迟写总量上限（默认约 osd_memory_target 的一部分）
bluestore_throttle_deferred_bytes # deferred 写入上限
bluestore_throttle_cost_per_io_hdd / _ssd
bluestore_throttle_cost_per_byte  # 每个 IO 的"成本"权重

# 观察是否被节流
ceph tell osd.N perf dump | jq '.throttle-bluestore_throttle | with_entries(select(.key|test("wait|lm")))'
#   .val / .max  → 当前值与上限；接近 max 说明在节流
#   .get_sum.wait / .put_sum.wait  → 等待时间与次数

# 缓解思路（按优先级）
# 1) 提升磁盘真实能力（这是根本）：加盘、换 SSD、做 db/wal 分离
# 2) 限制客户端并发（osd_client_message_size_cap 等反而是副作用，更推荐在客户端限流）
# 3) 适当调大 bluestore_throttle_bytes（只是把"变慢"推迟，治标）

7.4 ★ mclock：一个几乎没人注意到的"隐性 IOPS 天花板"

这是本文档最重要的一节。自 Quincy 起，BlueStore OSD 的默认调度器从 WPQ 换成了 mclock（osd_op_queue=mclock_scheduler）。mclock 需要知道"这块盘能跑多少 IOPS"才能按比例分配配额 —— 而这个数字来自 OSD 首次启动时跑的一次基准测试。
# ── 五分钟自检（无需停机）────────────────────────────
# 1. 当前用的是哪个调度器
ceph config show-with-defaults osd.0 | grep op_queue
#   osd_op_queue = mclock_scheduler    ← Quincy+ 默认

# 2. 每个 OSD 自认为的 IOPS 上限是多少
ceph config show-with-defaults osd.0 | grep -E 'mclock_max_capacity_iops'
# 3. 当前 profile
ceph config get osd.0 osd_mclock_profile

# 4. 看 OSD 日志里的基准测试结果
grep -i 'mclock' /var/log/ceph/ceph-osd.0.log | grep -i capacity
# ── 修复：手动告诉 Ceph 你的盘到底有多快 ─────────────
# 方式一：直接设全局（所有 OSD 同规格时）
ceph config set osd osd_mclock_max_capacity_iops_ssd 200000
ceph config set osd osd_mclock_max_capacity_iops_hdd 500

# 方式二：按 device class 分别设（混闪集群）
ceph config set osd.1 osd_mclock_max_capacity_iops_hdd 400   # 指定单 OSD
# 或对同 class 批量：
for o in $(ceph osd ls-tree node-01); do
  ceph config set osd.$o osd_mclock_max_capacity_iops_ssd 150000
done

# 方式三：改用 high_client_ops profile（生产推荐）
ceph config set osd osd_mclock_profile high_client_ops
#   client 预留从 50% → 60%，weight 1 → 2

# 方式四：极端情况回退到 WPQ（官方针对大规模 EC 集群的建议）
ceph config set osd osd_op_queue wpq      # ★ 需重启 OSD 生效
什么时候该回退到 wpq？官方文档（Tentacle mclock 配置参考）明确指出：大型 EC 集群在 recovery/backfill 期间可能触发 slow ops —— 因为 EC 恢复时的 sub-op 读会走高优先队列绕过 mclock 限流，导致源 OSD 被打满。临时方案就是切回 wpq。若你正遇到"EC 集群一做恢复就大面积 slow ops"，先试这个。

7.5 其他软件层瓶颈速查

瓶颈现象对策
PG 数过多CPU/内存占用高、peering 慢、扩容慢控制在每 OSD ~100 PG；开 autoscale
PG 数过少数据分布不均、单 PG 过大、迁移慢增加 pg_num
scrub 抢 IO周期性卡顿限速 + 时间窗（见运维手册）

version 不一致功能降级、性能下降统一版本

8瓶颈⑥：客户端与访问模式（最容易被忽视）

同样的集群，客户端配置不同，性能可以差 5~10 倍。这一层不需要改动集群，收益却常常最大。

8.1 四个决定性能的参数

① 并发深度（iodepth / numjobs）

影响最大。Ceph 是分布式系统，单线程串行 IO 会把网络往返延迟完全暴露（每次都要等 2ms）。
建议：fio 测试用 iodepth=32+、numjobs=4~16；数据库类业务也要保证足够并发。

② IO 大小（block size）

4K 随机 → IOPS 受限；1M 顺序 → 带宽受限。
建议：避免"小块 + 低并发"这种最差组合。大文件场景用 1M~4M。

③ 对象大小与条带（RBD）

rbd create --object-size 4M --stripe-unit ... --stripe-count ...
默认 object-size 4M。条带能让单个大 IO 并行落到多个对象/多个 OSD。
建议：大块顺序场景开条带（stripe-count 4~16）。

④ RBD 缓存

rbd_cache=true（用户态 librbd 默认开）。写缓存会把小写合并，显著提升随机写。
注意：默认 rbd_cache_writethrough_until_flush=false 意味着回写模式，断电可能丢数据！需要持久化语义时必须用 rbd_cache_writethrough_until_flush=true 或依赖上层 flush。

8.2 RBD / QEMU 侧调优参数

# ── librbd 客户端参数（/etc/ceph/ceph.conf 的 [client] 段）──
[client]
rbd_cache = true                       # 开启用户态缓存
rbd_cache_size = 1073741824            # 1 GB（默认 32MB，太小！建议 512M~4G）

# ── QEMU / KVM 侧（libvirt XML 或 qemu 命令行）──

# ── 内核 rbd（krbd）──
# 注意：krbd 不支持 rbd_cache 的全部特性，性能通常低于 librbd（QEMU 走 librbd）
# 大块顺序场景差距不大，随机小 IO 场景 librbd 明显更好

8.3 访问模式对性能的量级影响（实测参考）

访问模式相对性能说明
4K 随机写，iodepth=11×（最差）每次 IO 都要等完整网络往返 + 两次落盘，延迟完全暴露
4K 随机写，iodepth=3220~30×并发把延迟隐藏了，吞吐提升一个数量级
4K 随机写，iodepth=32 + RBD cache40~80×小写被合并且异步回写（注意数据安全语义）
1M 顺序写受限于网络/磁盘带宽此时看 MB/s 而非 IOPS
1M 顺序读（命中主副本）最高只读一份，可跑满单盘带宽
给业务方的建议（比调参更有效）：让业务批量提交 IO、使用更大的块、提高并发。很多时候"集群慢"的真相是业务在用"4K + iodepth=1"的方式写 —— 换成 1M + iodepth=16，同样的集群性能可以差几十倍。

9定量分析：算出你集群的理论上限

调优前先算账。如果实测值已经接近理论上限，那问题不在配置而在选型；如果实测只有理论的 1/3，那才值得深挖。

9.1 五步计算法

Step 1 · 单盘 IOPS：查规格或用裸盘 fio 实测（4K 随机写，iodepth=32）
Step 2 · 集群裸 IOPS = 单盘 IOPS × OSD 总数
Step 3 · 可用 IOPS（副本） = 集群裸 IOPS ÷ 副本数（size）
Step 4 · 网络校验：后端网带宽是否 ≥ 预期带宽 ×（size-1）
Step 5 · CPU 校验：总核心数是否 ≥ OSD 数 × 每 OSD 所需核心

9.2 三个算例

集群配置IOPS 计算带宽校验结论
A. HDD 容量型

9.3 容量规划（顺带复习）

可用容量 = 裸容量 ÷ 副本数 × (1 - 预留系数)
预留系数建议 25%~30%（用于：nearfull 缓冲、故障时的重建空间、扩容期间的迁移空间）

例：30×8TB = 240TB 裸容量，3 副本
→ 理论可用 80TB
→ 扣除 25% 预留 → 实际可交付约 60TB
→ 若还需能容忍 1 个节点（10 盘）故障后重建，需再验证剩余空间足够

EC 4+2：可用率 4/6 = 67%（对比 3 副本 33%），但写入放大 1.5x 且不支持部分写覆盖（小写需读改写）。

  osd_memory_target = 4294967296
【业务建议】用大块顺序 IO（1M+），避免大量小文件随机写
【预期】单盘顺序 ~200MB/s；集群顺序写 ≈ 盘数 × 200 / 3；随机写 ≈ 盘数 × 400 / 3

配方 B：混闪通用型（虚拟机 / 数据库 / 通用业务）

【目标】随机 IOPS 与容量平衡 —— 最常见的生产形态
【硬件】HDD 数据盘 + NVMe db/wal；或 SSD 缓存层 + HDD EC 冷层
【关键配置】
  osd_mclock_profile = high_client_ops
  osd_mclock_max_capacity_iops_hdd = 400      # ★ 实测后填
  osd_op_num_shards = 8 ; osd_op_num_threads_per_shard = 4
  osd_recovery_sleep = 0.1 ; osd_max_backfills = 1
  rbd_cache_size = 1073741824
【PG 规划】每 OSD ~100 PG
【预期】随机写比纯 HDD 提升 2~4 倍

配方 C：全闪高性能（数据库 / 高并发 OLTP）

【目标】极致低延迟与高 IOPS
【硬件】企业级 NVMe（带掉电保护），不分离 db（或 db 同 NVMe 分区）；
       前端 25GbE + 后端 100GbE；CPU 高主频 ≥2.5GHz，关闭节能
【关键配置】★ 按顺序逐项确认
  1. osd_mclock_max_capacity_iops_ssd = <实测值>     # ★ 最关键！默认 21500 会严重限制
  2. osd_mclock_profile = high_client_ops
  3. osd_op_num_shards = 16 ; osd_op_num_threads_per_shard = 4~8
  4. osd_memory_target = 8589934592                  # 8 GB
  5. bluestore_csum_type = none                      # 可选，省 CPU
  6. bluestore_rocksdb_options = compression=kNoCompression,...
  7. ms_async_op_threads = 8 ; ms_bind_msgr2 = true
  8. MTU 9000 全网统一；RSS 多队列 + 中断绑核
  9. 关闭 THP，CPU performance 模式
【验收】4K 随机写 P99 延迟应 < 2ms；若 > 5ms 说明还有瓶颈未排除
【注意】全闪集群瓶颈通常在 CPU/网络/mclock，而不是磁盘

配方 D：EC 冷存储（海量归档 / 影像 / 日志）

【目标】最大化可用容量
【配置】ceph osd erasure-code-profile set ec42 k=4 m=2 plugin=isa crush-failure-domain=host
        ceph osd pool create cold 1024 1024 erasure ec42
        ceph osd pool set cold allow_ec_overwrites true     # 只有 RGW/需要覆盖写时才开
【关键配置】
  osd_op_queue = wpq          # ★ 官方建议：大规模 EC 集群在恢复期用 wpq 避免 slow ops
  plugin = isa（ISA-L 加速）而非 jerasure（默认），EC 计算性能提升 2~5 倍
【注意】
  · EC 池不支持 RBD（除非开启 allow_ec_overwrites 且有额外风险）
  · 小写有读改写惩罚（RMW），适合大对象顺序写
  · 故障域必须 ≥ (k+m) 个，否则 PG 会 undersized

配方 E：Kubernetes / OpenStack 场景（RBD）

【目标】稳定、可预期、避免单卷抖动影响全局
【关键配置】
  # 客户端（每个节点）
  rbd_cache = true ; rbd_cache_size = 1073741824
  # QEMU 使用 librbd 而非内核 rbd
  <driver name='qemu' type='raw' cache='none' io='native' iothread='1'/>
  # 每卷 QoS 限制（避免"吵闹的邻居"）
  rbd config image set <pool>/<img> rbd_qos_iops_limit 3000
  rbd config image set <pool>/<img> rbd_qos_bps_limit 104857600
  # 集群侧
  osd_mclock_profile = high_client_ops
  # 镜像特性：若不用快照，关闭 object-map/fast-diff 减少元数据
  rbd feature disable <pool>/<img> object-map fast-diff
【注意】K8s 场景务必为不同业务建不同 pool，便于隔离与限流

配方 F：RGW 对象存储（海量小文件 / S3）

【目标】高并发小对象读写
【关键配置】
  # bucket index 分片（★ 最重要，单分片超过 10 万对象就会热点）
  ceph config set client.rgw bucket_index_max_shards 32      # 按对象规模设 16~128
  radosgw-admin bucket reshard --bucket=X --num-shards=32
  # RGW 线程
  rgw_thread_pool_size = 512
  rgw_max_concurrent_requests = 2048
  rgw_cache_enabled = true ; rgw_cache_lru_size = 10000
  # index 池建议放在 SSD 上（★ 元数据热点）
  # GC
  rgw_gc_max_objs = 32 ; rgw_gc_obj_min_wait = 3600
  # 架构
  多 RGW 实例 + HAProxy 负载均衡；RGW 与 OSD 分离部署或共部署视规模而定
【监控】radosgw-admin gc list | wc -l   # GC 积压是常见性能杀手

13调优误区与验证

13.1 十大常见误区

误区真相
❌ "加更多 OSD 一定能更快"受限于网络、CPU、PG 规划。OSD 太多而 CPU/内存不足，反而更慢（进程开销、心跳风暴）。
❌ "调大各种 buffer 就能快"buffer 只是缓冲，不改变吞吐上限。调太大只会导致延迟更高、内存压力更大。
❌ "副本数从 3 降到 2 提升 50% 性能"确实会提升写入性能约 1/3，但数据可靠性断崖下降。2 副本下坏一块盘就是 degraded，第二块坏了就丢数据。
❌ "全闪集群不用管网络"恰恰相反。全闪集群最常见的瓶颈就是网络和 CPU，因为磁盘已经不是短板了。
❌ "用 fio 测本地盘的数字代表 Ceph 性能"要除以副本数，还要减去网络与软件栈开销。参见第 9 章。
❌ "PG 越多越好"PG 过多会增加内存/CPU 开销、peering 变慢、扩容变慢。每 OSD ~100 是甜点。
❌ "关掉 scrub 能提升性能"短期有效，长期会导致数据静默损坏无法被发现。正确做法是限速 + 错峰，而不是关闭。
❌ "所有参数用一套模板"HDD、混闪、全闪、EC 的最优配置完全不同。照抄模板是性能事故的常见来源。
❌ "压测只看平均值"P99/P999 比平均值重要得多。平均 5ms 但 P99 200ms 的集群，业务体感是"卡"。
❌ "一次改十几个参数然后测"无法归因。改完变快了不知道是哪个起作用，变慢了不知道该回滚哪个。

13.2 调优的完整闭环

① 建基线 → 四段压测（第 10 章），记录 IOPS / 带宽 / 平均延迟 / P99
② 算理论 → 第 9 章公式，判断实测与理论的差距
③ 定瓶颈 → 五层/六层定位，用监控数据锁定具体环节
④ 改一项 → injectargs 临时生效，或 ceph config set
⑤ 复测 → 同样的命令、同样的持续时间、同样的并发
⑥ 对比 → 用 10.3 的模板记录，有效则持久化，无效则回滚
⑦ 沉淀 → 把有效配置写进部署文档/Ansible 变量，下次新集群直接复用
最后的心法：Ceph 调优不是"堆参数"，而是不断问"瓶颈现在在哪一层"。每消除一个瓶颈，下一个瓶颈就会浮出水面 —— 这是正常现象，说明前一步的调优生效了。当实测值达到理论值的 60%~80%（HDD）或 40%~60%（全闪），就该停止调参，转而从业务访问模式和硬件选型上想办法了。

14.1 调优检查清单（新集群上线前逐项确认）

□ 硬件层
  □ CPU 设为 performance 模式，关闭 C-State / 节能
  □ 关闭 swap（或 swappiness=1）
  □ I/O 调度器：HDD=mq-deadline，NVMe=none
  □ 关闭 THP
  □ RAID 卡为 JBOD/HBA 模式（★ 绝对不要用硬件 RAID 做 OSD）
  □ 磁盘写缓存策略与 BBU 匹配
□ 网络层
  □ 前端网与后端网物理分离
  □ MTU 9000 全网一致（含交换机），已用 ping -M do 验证
  □ 无 CRC/丢包错误（ethtool -S）
  □ 多队列网卡 RSS 已开启，中断均衡
  □ 内核 TCP buffer 参数已调优
□ Ceph 层
  □ mclock 容量值已按实测设置（★ 全闪必做）
  □ osd_mclock_profile = high_client_ops
  □ db/wal 布局合理，db 容量 ≥ 主盘 4%
  □ PG 数符合每 OSD ~100
  □ osd_memory_target 按介质设置
  □ recovery / scrub 限速参数已配置
  □ balancer 已开启（upmap 模式 + 时间窗）
□ 客户端层
  □ rbd_cache_size 已从默认 32M 调大
  □ IO 模式合理（避免 4K + 低并发）
  □ 关键业务已配置 QoS 限流
□ 验证
  □ 四段压测基线已记录
  □ 监控告警已配置（slow ops / 延迟 / 容量 / PG）
  □ 故障演练已完成（拔盘、断网、OSD 宕机）
