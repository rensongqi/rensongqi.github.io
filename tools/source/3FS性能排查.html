1现象：延迟高在哪里

故障现场。某 GPU 训练集群（TF 机型）批量出现 3FS 读写延迟高、性能差：除 013、014 两台节点正常外，其余节点全部异常。表现为——单进程 fio 或 cp 拷贝大文件，异常节点吞吐比正常节点下降约 1/3；4K 小文件随机读写延迟相差约 10 倍。

存储类问题的第一步永远是量化差异：用同一套 fio 参数在正常与异常节点各压一遍，看延迟分布到底差多少。测试命令（任何一台机器上可直接重跑）：

fio --name=randread \
    --filename=/3fs/cache/test/test.file \
    --size=4G \
    --bs=4k \
    --rw=randread \
    --ioengine=io_uring \
    --iodepth=1 \
    --numjobs=1 \
    --direct=1 \
    --runtime=60 \
    --time_based \
    --group_reporting

本次用于对照的四台节点（主机名与内网 IP 已脱敏，双网卡：ens1np0 走 TCP 业务面，ens4np0 走 RoCE 存储面）：

集群内其余节点（gpu-001/005/006/007/008/009/010/011/012/016 等）表现与 008/009 一致，均为异常。

3.1 网卡队列、PFC、DSCP

RoCE 对 QoS 配置极其敏感，第一项先核对 ens4np0 的队列与 PFC：mlnx_qos -i ens4np0。异常节点输出与标准完全一致——trust 走 DSCP，PFC 只开在优先级 5，dscp2prio 映射、buffer、tc 带宽分配逐项比对无差异。配置出自同一份标准部署脚本，关键段落如下（交付标准，可直接复用）：

#!/bin/bash
MLNX_ROCE_TOS=162
MLNX_ROCE_CNP_DSCP=48
COMPUTE_IFACES=(ens4np0)
for iface in "${COMPUTE_IFACES[@]}"; do
    mlnx_qos -i "$iface" --trust=dscp >/dev/null
    mlnx_qos -i "$iface" --cable_len=30
    mlnx_qos -i "$iface" --pfc 0,0,0,0,0,1,0,0 >/dev/null
    mlnx_qos -i "$iface" --prio_tc=0,1,2,3,4,5,6,7 >/dev/null
    mlnx_qos -i "$iface" --dscp2prio='set,40,5' >/dev/null   # 计算面队列走 TC1
    mlnx_qos -i "$iface" --dscp2prio='set,48,6' >/dev/null   # 流控队列走 TC0
    mlnx_qos -i "$iface" -s ets,ets,ets,ets,strict,strict,strict,strict --tcbw=9,1,80,10,0,0,0,0 >/dev/null 2>&1
    mlnx_qos -i "$iface" --buffer_size 19872,220896,0,0,0,0,0,0 >/dev/null 2>&1
    echo 1 > /sys/class/net/"$iface"/ecn/roce_np/enable/5    # 优先级5开 ECN
    echo 1 > /sys/class/net/"$iface"/ecn/roce_rp/enable/5
    echo "$MLNX_ROCE_CNP_DSCP" > /sys/class/net/"${iface}"/ecn/roce_np/cnp_dscp
    mlnx_qos -i "$iface" --prio2buffer=0,0,0,0,0,1,0,0 >/dev/null
done

HCA=(mlx5_17)
for mlx in "${HCA[@]}"; do
    cma_roce_mode -d "$mlx" -p 1 -m 2 1>/dev/null
    cma_roce_tos -d "$mlx" -t "$MLNX_ROCE_TOS" 1>/dev/null
    echo "$MLNX_ROCE_TOS" > /sys/class/infiniband/"$mlx"/tc/1/traffic_class
    mlxreg -d "$mlx" --reg_name ROCE_ACCL \
      --set 'roce_slow_restart_en=0x0,roce_adp_retrans_en=0x1,roce_tx_window_en=0x0,roce_slow_restart_idle_en=0x0' \
      --yes >/dev/null
done

5根因：C-state 未禁用

执行 cpupower idle-info 对比两端：

一句话根因：正常节点的 C1_ACPI 和 C2_ACPI 都是禁用状态，异常节点没有禁用。是 CPU 休眠状态（C-state）引入的固定唤醒延迟，叠加到了每一次中断响应上。

5.1 C-state 是什么

现代 Intel CPU 在空闲时会进入不同深度的休眠状态省电，「睡」得越深，醒过来要花的时间越长：

状态说明Exit Latency（退出延迟）
POLL / C0忙等待 / 运行态0
C1_ACPI轻度休眠约 1μs
C2_ACPI深度休眠约 170μs

cpupower idle-info 里的 Latency 字段就是 CPU 从该睡眠态被唤醒、恢复到可执行指令状态所需的时间。

5.2 开启状态发生了什么

C1_ACPI、C2_ACPI 均启用时，CPU 在两次网卡中断之间的空闲窗口里，会被 menu 调度器（cpuidle governor）根据历史空闲时长预测，主动切进 C2_ACPI 省电。此时一个网络包（比如 ICMP echo）到达触发硬件中断，CPU 要先从 C2 花约 170μs 唤醒，再加上中断响应和调度延迟——这笔开销直接叠加到 ping 的 RTT 里，也叠加到 fio 每一个 4K IO 的中断处理路径上。

关闭状态下则完全相反：所有 C-state 被 DISABLED，CPU 核心被锁在浅层甚至运行态，中断到达时几乎零延迟响应——所以正常节点 ping 延迟低而稳（抖动也小），RDMA 又因为本身旁路 CPU 而两头都不受影响。前面三组矛盾现象到这一步全部对上。

6修复与验证

6.1 临时禁用（重启失效）

# 先看清楚本机的 idle 状态列表与 index（不同机器/BIOS 列表可能不同，有的有 C6）
cpupower idle-info

# 按 index 禁用（本例 C1_ACPI=1、C2_ACPI=2）
cpupower idle-set -d 2 -d 1

注意 state index 是动态的，先用 idle-info 确认序号再禁，不要照抄别人的数字。

6.2 持久化（重启生效）

cpupower idle-set 重启后失效，长期方案写进内核启动参数，编辑 /etc/default/grub：

GRUB_CMDLINE_LINUX="... intel_idle.max_cstate=1 processor.max_cstate=1"
update-grub
reboot

6.3 验证

先只禁 C2（170μs 退出延迟，是大头）：性能提升约 70%；再把 C1 一并禁用（C1 只有约 1μs，影响小，但一起禁更彻底）：读写延迟与正常机型拉齐——90%+ 的 IO 延迟回到 250μs 档：

修复确认。异常节点在禁用 C1/C2 后，fio 延迟分布、ping RTT 均与正常节点一致；集群批量按 6.1 + 6.2 处理后故障消除。
