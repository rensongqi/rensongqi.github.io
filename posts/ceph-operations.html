1运维对象地图：先知道你在管什么

Ceph 运维的本质是管理五类对象，所有命令都围绕它们展开。遇到告警时，第一件事是判断"这是哪一层的锅"，而不是急着敲命令。

黄金三步：任何告警先回答三个问题 —— ① 集群现在 HEALTH 是什么（ceph health detail）？② 影响范围多大（几个 OSD / 几个 PG / 哪个 pool）？③ 是突发的还是渐进的（对比昨天这个点的监控）？答不上来就先别动手。

各对象的"健康标准"速判

对象健康标准异常时的典型表现
MON奇数个（3/5），quorum 完整，时钟偏移 < 0.05s，磁盘 < 60%集群整体不可读写、mon election、clock skew
MGR1 主 1 备，mgr stat 显示 active+standbydashboard 打不开、prometheus 无数据、PG 不自动均衡
OSD全部 up 且 in，commit/apply 延迟正常，VAR 0.8~1.2slow ops、PG degraded、容量不均
PG100% active+clean，无 stuck/inconsistent业务 IO 卡顿、数据不一致风险
Pool使用率 < 70%（HDD 建议更低），PG 数合理nearfull / backfillfull / full → 只读

2命令体系全景：记住规律而不是背命令

2.1 命令命名规律（看懂这节等于少背 100 条）

Ceph 命令是树状结构，ceph <对象> <动作> [参数]。掌握规律后可以"猜"出命令。

看列表

ls / stat / dump / tree
例：ceph osd ls、ceph osd tree、ceph osd dump

看详情

detail / ... <id> get
例：ceph health detail、ceph osd.0 perf dump

改配置

set / unset / ceph tell ... injectargs
例：ceph osd set noout、ceph tell osd.* injectargs '--osd-max-backfills=1'

动作动词对照：
ls 列表 → stat 摘要 → dump 全量（JSON/详细）→ get 取单个 → set 设置 → add/rm 增删 → create/delete 建删 → enable/disable 开关 → fail 强制切换 → repair/scrub 修复
三条最省时间的用法：
① ceph --admin-daemon /var/run/ceph/ceph-osd.0.asok <cmd> —— 绕过网络直连本地 OSD 拿数据，集群卡死时救命；
② ceph tell osd.* <cmd> —— 对所有 OSD 批量下发（改参数、清 slow ops 计数都用它）；
③ --format=json-pretty + jq —— 任何命令加这个后缀都能被脚本消费。

2.2 集群与健康（每天必敲）

# ── 看状态 ──────────────────────────────────────────
ceph -s                       # 状态摘要（最常用）
ceph -w                       # 持续刷新（按 Ctrl+C 退出）
ceph health                   # 只要 HEALTH_OK / WARN / ERR
ceph health detail            # ★ 出问题时第一个敲这个，直接告诉你原因
ceph status --format=json-pretty | jq '.health.cheks'   # 脚本消费

# ── 看容量 ──────────────────────────────────────────
ceph df                       # 池维度（USED / AVAIL / USED%）
ceph df detail                # 含 raw used、压缩收益
ceph osd df                   # OSD 维度（★ 看 VAR 列判断均衡）
ceph osd df tree              # 按 host/rack 聚合，看节点间是否均衡

# ── 看实时流量 ──────────────────────────────────────
ceph -s                       # 头部有 client io: read/write
watch -n1 'ceph -s | tail -5' # 盯 IO
rados df                      # 池级对象数与占用
ceph osd pool stats           # 每个池的 IO 速率

# ── 集群开关（运维必备）────────────────────────────
ceph osd set noout            # ★ 禁止 OSD 自动 out（换盘/停机维护前必做）
ceph osd unset noout          # 恢复
ceph osd set norecover        # 暂停恢复
ceph osd set nobackfill       # 暂停回填（比 norecover 更常用，只停全量回填）
ceph osd set noscrub; ceph osd set nodeep-scrub   # 停 scrub（压测/应急时）
ceph osd set full             # 人工置 full（紧急熔断，慎用）
ceph osd unset nobackfill noscrub nodeep-scrub noout   # 一次性全部解除
ceph osd dump | grep flags    # 查看当前设置了哪些 flag
flag 使用铁律：noout 设了一定要记得 unset。见过太多次"三个月前维护时设了 noout 忘了取消"，结果后来真有 OSD 挂了却不触发恢复，直到第二块盘也挂 → 数据丢失。建议在变更单里强制写"解除时间"。

2.4 OSD（运维最密集的一块）

# ── 拓扑与状态 ──────────────────────────────────────
ceph osd tree                 # 树状：host / rack / osd 的权重与状态
ceph osd tree up              # 只看 up 的
ceph osd tree out             # 只看 out 的
ceph osd stat                 # 一行摘要（x osds: y up, z in）
ceph osd dump                 # 全量（含 flags、pool、pg_num）
ceph osd metadata 0           # ★ 单盘硬件信息：型号/固件/rotational/bluestore 布局
ceph osd find 3               # osd.3 在哪台机器、crush 位置

# ── 性能（★ 排障核心）──────────────────────────────
ceph osd perf                 # ★ 每个 OSD 的 commit_latency / apply_latency（ms）
ceph osd perf | sort -k3 -n -r | head   # 找出最慢的 10 个
ceph osd.12 perf dump         # 单 OSD 全部计数器（几百项）
ceph osd.12 perf dump | jq '.bluestore.kv_commit_lat, .osd.op_w_latency'
ceph tell osd.12 dump_ops_in_flight     # ★ 正在跑的慢请求（见第 3 章）
ceph tell osd.12 dump_historic_ops      # 历史上最慢的请求
ceph tell osd.12 dump_blocked_ops       # 被阻塞的（等 scrub / 等 pg lock）
ceph tell osd.12 dump_ops_in_flight --format=json-pretty | jq '.ops[0].description'
ceph daemon osd.12 dump_osd_network 1700000000   # 指定时间点的网络延迟矩阵
# ── 上下线与剔除 ────────────────────────────────────
ceph osd out 12               # 标记 out（开始迁移数据）★ 缩容第一步
ceph osd in 12                # 标记 in（数据迁回）
ceph osd down 12              # 标记 down（不迁移，仅测试用，慎点）
ceph osd stop 12              # 停进程（等效 systemctl stop ceph-osd@12）
ceph osd reweight 12 0.8      # ★ 临时降权（0~1），不触发大范围迁移，止血首选
ceph osd reweight 12 1.0      # 恢复
ceph osd crush reweight osd.12 3.6      # ★ 按容量改 crush weight（TB 数）
ceph osd crush remove osd.12            # 从 crush 树移除
ceph osd purge 12 --yes-i-really-mean-it  # ★ 一条命令完成 out+crush rm+auth rm
ceph osd safe-to-destroy 12   # ★ 剔除前必问：这个 OSD 上的数据是否可安全丢弃
ceph osd destroy 12 --yes-i-really-mean-it
ceph osd lost 12 --yes-i-really-mean-it  # 极端情况：强制宣告丢失（★ 高危）

# 单盘 scrub（怀疑坏道 / 校验失败时）
ceph osd scrub 12             # 轻量 scrub（只比元数据）
ceph osd deep-scrub 12        # 深度 scrub（比全部数据内容，IO 压力大）
ceph pg repair <pgid>         # 发现 inconsistent 后修复（★ 先确认哪份是权威）
reweight vs crush reweight 怎么选？

osd reweight（0~1）是"覆盖层"，不改 crush map，立刻生效、迁移量小，用于临时救急（某盘慢/快满）。
osd crush reweight 改的是 crush map 里的 weight（=TB 数），永久生效，用于磁盘容量真的变了（换大盘/换小盘）。

out 和 down 的区别

down = 进程不在（心跳断），但数据仍算它的，PG 会 degraded 但不迁移。
out = 数据不算它的了，立刻触发迁移。
短暂停机维护 → 只需 down（配合 noout）；永久摘除 → out。

3OSD slow ops 深度排查

slow ops（慢请求）是 Ceph 运维里最高频、也最容易被误判的告警。它的含义是"某个请求在 OSD 内部排队或执行的时间超过了阈值"，但它并不等于这块盘坏了 —— 它只是"结果"，根因可能在五个不同层级。这一章给一套可复现的排查路径。

3.1 什么是 slow ops：两种告警要分清

告警出处含义与判定
SLOW_OPS
slow request N sec old		OSD 日志
ceph health detail		客户端请求在 OSD 里滞留 > osd_op_complaint_time（默认 30s）。业务可感知的卡顿，优先级最高。
OSD_SLOW_PING_TIME
osd.N 慢心跳		OSD 间心跳后端网络（cluster network）或某 OSD 响应慢，ping 时间超 osd_heartbeat_grace 比例。可能是网络抖动，不一定影响 IO。
MON_DOWN / MON_CLOCK_SKEWMON常与 slow ops 伴生，是"控制面不稳"的信号。
PG_AVAILABILITY / PG_DEGRADEDPG 层副本数不足，读可能变慢（要重试别的副本）。
关键阈值参数（可用 ceph tell osd.* injectargs 临时改）：
osd_op_complaint_time = 30　超过多久记为 slow request
osd_op_log_threshold = 5　每秒最多打印几条 slow 日志（避免刷爆日志）
osd_op_history_size = 20　保留多少条 historic op
osd_op_history_duration = 600　历史保留时长
osd_heartbeat_grace = 20　心跳宽限，与 osd_heartbeat_interval(6) 配合
osd_mon_report_interval = 5 / mon_osd_report_timeout = 900　上报与判死

3.2 五层定位法：从"哪一层慢"反推根因

3.3 抓取现场的三把刀

slow ops 是瞬时现象，等你看告警时可能已经恢复。所以要抓"现场"。

① dump_ops_in_flight —— 现在卡的是什么

ceph tell osd.12 dump_ops_in_flight --format=json-pretty | jq '.ops[] | {
  desc: .description, dur: .duration, type: .type,
  client: .client_info.client, events: [.events[].event] }'   # 精简输出

# 典型输出解读
{
  "description": "osd_op(client.12345.0:88213 3.4f 3:4f3d2c1b::rbd_data.xxx.0000000000000a1f:12 [write 4096~4096] ...)",
  "duration": 47.318,          # ★ 已经卡了 47 秒
  "type": "osd_op",
  "events": [
    "started",                 # 进入队列
    "commit_queued_for_journal_write",   # 排进 journal(bluestore wal) 写队列
    "queued_for_journal_write",
    "doing_journal_write",     # ★ 卡在写 WAL/盘 → 磁盘层问题
    "done_journal_write",
    "commit_sent"              # 已回复 ack
  ]
}
events 数组就是"案发现场录像"。卡在哪个 event 就指向哪个组件：
• 只有 started / 一直 queued → 队列积压（OSD 忙或 throttling）
• 停在 doing_journal_write → WAL 盘慢（NVMe 故障或 db 分区写满）
• 停在 waiting for rw locks → 对象/集合锁竞争（常见：rbd 大并发写同一对象、RGW 索引热点）
• 停在 waiting for scrub / blocked by scrub → scrub 抢 IO
• 停在 reached_pg + waiting_peering → PG 在做 peering，即该 PG 有副本异常
• 出现 sub_op 相关 → 主 OSD 在等从 OSD（网络或从盘慢）

② dump_historic_ops —— 过去了也要知道谁最慢

ceph tell osd.12 dump_historic_ops --format=json-pretty | \
  jq -r '.ops | sort_by(-.duration) | .[0:5][] | "\(.duration)s  \(.description[0:90])"'

# 建议先调大保留量（默认只留 20 条，很快被覆盖）
ceph tell osd.* injectargs '--osd_op_history_size=200 --osd_op_history_duration=1800'

③ dump_blocked_ops / perf dump —— 看是否是 scrub 或锁

ceph tell osd.12 dump_blocked_ops
ceph tell osd.12 perf dump | jq '{opq: .osd.op_queue_ops, qlen: .osd.op_wip,
   wal: .bluestore.kv_commit_lat, apply: .bluestore.commit_lat.avgcount,
   commit: .osd.op_w_latency, subop: .osd.op_r_out_bytes}'

3.4 根因速查表（按出现频率排序）

根因典型特征确认方法处理动作
① 慢盘 / 亚健康盘
（最常见）		个别 OSD 的 commit 延迟长期 50~500ms，其他盘 <10msceph osd perf 排序；iostat -xmt 1 看 awaitosd reweight 降权止血 → 择机 out 换盘

④ recovery / backfill 洪峰ceph -s 的 io.recovery 很大；扩缩容或 OSD 反复 up/down 后出现ceph -s；ceph pg statosd_max_backfills=1、osd_recovery_max_active=1、限速（5.4 节）
⑤ deep scrub 抢 IO周期性（每周/每天固定时段）卡顿，与业务高峰重叠ceph pg dump | grep scrubbing调整 scrub 时间窗 osd_scrub_begin_hour/end_hour，或临时 nodeep-scrub
⑥ 网络丢包 / 抖动多个 OSD 同时 slow，且与某台交换机/网卡相关ethtool -S 的 rx_/tx_errors、retrans；sar -n DEV换光模块/网线/端口；检查 bonding 模式与 MTU
⑦ 前端网打满客户端带宽跑满（大块顺序读/写、备份任务）交换机端口 ≥90%；ceph -s 的 client io 巨大限速业务；扩前端网（bond/万兆改 25G）；错峰备份
⑧ OSD 单核 CPU 打满top -H 里某个 tp_osd_tp/msgr-worker 线程 100%，整体 CPU 不高top -H -p <pid>增加 osd_op_num_threads_per_shard；升级 CPU；开 RDMA/msgr V2 减少软中断
⑨ 内存不足 / swapOSD 被 OOM 或延迟整体抬升，free 里 swap 有使用free -g；dmesg | grep oom按每 OSD 4~8G 规划内存；vm.swappiness=1；降低 OSD 内存目标
⑩ MON 频繁选举 / 时钟偏移ceph -s 的 mon quorum age 一直是几秒；clock skew 告警ceph health detail；chronyc sources修 chrony；给 MON 独立盘；保证 MON 数 ≥3 且奇数
⑪ RGW 索引池热点只有 RGW 慢，且单 bucket 对象数上亿radosgw-admin bucket stats；索引池 OSD 延迟高开 index sharding（bucket_index_max_shards）；或改动态分片
⑫ 客户端问题仅单台宿主机慢，集群侧无异常客户端 dmesg；librbd 版本升级 librbd/内核；检查客户端自身 CPU/网络

3.5 六个真实案例（现象 → 排查 → 结论 → 修复）

案例 1：全集群周期性卡顿，每周日凌晨 3 点准时发生
现象：周日凌晨业务报 IO 超时，白天一切正常。
排查：ceph -s 显示大量 PG 处于 scrubbing；查参数 osd_scrub_begin_hour=0 / end_hour=24，deep scrub 周期 7 天，恰好落在周日。机械盘集群 deep scrub 全量读盘，把 IOPS 吃光。
结论：deep scrub 与业务窗口重叠 + 未限速。
修复：ceph tell osd.* injectargs '--osd_deep_scrub_interval=1209600 --osd_scrub_begin_hour=1 --osd_scrub_end_hour=6 --osd_scrub_sleep=0.1'，并写入 ceph.conf 持久化。对 HDD 集群，scrub 期间 sleep 参数比什么都管用。
案例 2：扩容后持续 slow ops 三天不消
现象：新加 12 块 OSD 后，recovery 一直跑，业务延迟从 5ms 涨到 100ms+。
排查：ceph -s 中 io.recovery: 800 MB/s；ceph osd df 显示新 OSD 已经 60%，老 OSD 才降到 85% —— 迁移目标选择不均。
结论：backfill 并发过高（默认 1，但 osd_recovery_max_active 默认 3，加上 osd_recovery_sleep 未设），把前端网和磁盘 IO 占满。
修复：ceph tell osd.* injectargs '--osd_max_backfills=1 --osd_recovery_max_active=1 --osd_recovery_sleep=0.1 --osd_recovery_op_priority=1'（优先级降到最低，让业务 IO 优先）。恢复后 unset。
案例 3：NVMe 集群用了一年后性能下降 60%
现象：全闪集群随机写 IOPS 从 12 万掉到 5 万。
排查：ceph tell osd.5 perf dump | jq '.bluestore' 发现 bluefs_db_total 与 bluefs_db_used 接近，spillover 计数不断涨 —— block.db 溢出，元数据被迫写到慢的主设备（HDD 或满盘 SSD）。
结论：db 分区（每盘 10G）太小，Rocksdb 元数据增长后溢出。
修复：① 立即：ceph tell osd.* compact（手动触发 RocksDB 压缩，回收空间，临时缓解）；② 根治：重建 OSD，db 按主盘容量 4%（HDD）分配，并做 compaction 定期任务。这是全闪/混闪集群最常见的性能衰减原因。
案例 4：某台机器上所有 OSD 同时 slow
现象：node-07 上的 12 个 OSD 全部 commit 延迟 > 200ms，其他节点正常。
排查：登机器 iostat -xmt 1 发现所有盘 %util 都 100% 但 r/s+w/s 很低 —— 不是真 IO；dmesg 有 megaraid_sas: ... reset adapter。
结论：RAID 卡故障/固件 bug，控制器反复重置。典型"伪装成 Ceph 问题的硬件问题"。
修复：ceph osd set noout → 整机 out → 停机更换/升级 RAID 卡固件 → 恢复。教训：Ceph 必须用 HBA/JBOD 模式，不要用硬件 RAID。
案例 5：PG 卡在 active+remapped，永远不 clean
现象：10 个 PG 长期 remapped，ceph -s 一直 HEALTH_WARN。
排查：ceph pg <pgid> query 显示 up 与 acting 不一致，blocked 字段为 backfill: backfill_full。
结论：目标 OSD 的使用率超过 osd_backfillfull_ratio（默认 90%），拒绝接收回填数据。
修复：① 短期：调低源 OSD 权重让数据先分散；② 中期：清数据/扩容；③ 注意不要简单调高 backfillfull 阈值绕过，那会让某个 OSD 直接冲到 full 导致集群只读。
案例 6：RGW 上传小文件特别慢，块存储却正常
现象：S3 上传 100KB 对象要 2 秒，RBD 一切正常。
排查：ceph osd perf 正常；radosgw-admin bucket stats --bucket=X 显示该 bucket 有 1.2 亿对象，num_shards=0（老版本默认不分片）。
结论：bucket index 单分片热点，所有上传都串行写同一个 index 对象所在的 OSD。
修复：新 bucket 设 radosgw-admin bucket reshard --num-shards=...；全局配置 bucket_index_max_shards（RGW）。单分片建议不超过 10 万对象。

3.6 止血十招（按风险从低到高，出事时依次尝试）

  1. 先确认范围：ceph health detail + ceph osd perf | sort -k3 -nr | head，别盲目操作。
  2. 停 scrub：ceph osd set noscrub; ceph osd set nodeep-scrub。零风险，见效快。
  3. 降 recovery 优先级：ceph tell osd.* injectargs '--osd_recovery_op_priority=1 --osd_max_backfills=1'。
  4. 给慢盘降权：ceph osd reweight 12 0.7（比 out 温和，迁移量小）。
  5. 单盘限速：ceph tell osd.12 injectargs '--osd_recovery_max_active=1'。
  6. 清理积压：RGW 场景 radosgw-admin gc process（GC 队列积压会拖慢写入）。
  7. 触发 RocksDB 压缩：ceph tell osd.12 compact（db 溢出时非常有效，但会短暂增加 IO）。
  8. 释放缓存：CephFS 场景 ceph tell mds.* cache drop（MDS 缓存过大导致卡顿）。
  9. 重启单个慢 OSD：systemctl restart ceph-osd@12（先 set noout！否则触发大规模迁移）。
  10. 整机隔离：ceph osd crush reweight-by-utilization 或直接把问题 host 的 OSD 全部 out —— 最后手段，需要有足够剩余容量。
绝对不要做的三件事：① 不看 ceph osd safe-to-destroy 就 purge OSD；② 在没 set noout 的情况下批量重启 OSD；③ 为了消除告警而把 nearfull/full 阈值往上调（等于拆掉烟雾报警器）。

4.3 手动均衡（理解原理 + 应急用）

# ① 按容量自动重算 crush weight（适合"磁盘规格不一致"导致的长期不均）
ceph osd crush reweight-by-utilization 105     # 105 = 目标：超过均值 105% 的才动
# 效果：把使用率高的 OSD 权重调低，低的使用率调高；会触发迁移
# 注意：它会把 weight 改成非整数（如 3.53），后续换盘需手动修正

# ② 按 PG 数自动重算（更温和，推荐 HDD 集群首选）
ceph osd crush reweight-by-pgs 105

# ③ 单个 OSD 临时降权（止血首选，迁移量最小）
ceph osd reweight 12 0.85

# ④ 手工 upmap（把 3.4f 这个 PG 的第 0 个副本从 osd.5 挪到 osd.9）
ceph osd pg-upmap-items 3.4f 5 9
ceph osd rm-pg-upmap-items 3.4f               # 撤销

# ⑤ 测试模式：先看会迁移多少，不真做（★ 变更前必做）
ceph osd crush reweight-by-utilization 105 --no-increasing   # 只降不升
ceph balancer eval                            # 看当前均衡评分
ceph balancer eval-verbose                    # 看每个 pool 的评分
balancer eval 的评分怎么看：输出类似 current cluster score 0.031245 (lower is better)。数值越小越均衡。一般 < 0.05 已经很好；> 0.15 说明有明显热点。执行优化计划后再 eval 一次对比。

4.4 balancer 自动均衡（生产推荐做法）

# ── 启用与模式选择 ─────────────────────────────────
ceph balancer on                      # 开启（默认 upmap 模式）
ceph balancer off
ceph balancer mode upmap              # ★ 推荐：Luminous+，迁移量最小，兼容所有客户端
ceph balancer mode crush-compat       # 兼容旧客户端（如老的 librbd/kernel rbd）
ceph balancer mode read               # 只读模式：只出计划，不执行（演练用）
ceph balancer status                  # 查看当前状态与最近执行记录

# ── 手动触发一次（不必等自动周期）───────────────────
ceph balancer optimize plan1          # 生成名为 plan1 的优化计划
ceph balancer eval plan1              # 评估这个计划执行后的评分
ceph balancer show plan1              # 看计划内容（要迁移哪些 PG）
ceph balancer execute plan1           # 执行
ceph balancer rm plan1                # 删除计划

# ── 参数调整 ───────────────────────────────────────
ceph config set mgr mgr/balancer/active true
ceph config set mgr mgr/balancer/mode upmap
ceph config set mgr mgr/balancer/sleep_interval 300      # 每 5 分钟评估一次
ceph config set mgr mgr/balancer/begin_time 0100         # 只在凌晨 1 点后运行
ceph config set mgr mgr/balancer/end_time 0600
ceph config set mgr mgr/balancer/max_misplaced 0.05      # ★ 同时最多 5% 的 PG 处于错位，控制影响
ceph config set mgr mgr/balancer/target_max_misplaced_ratio 0.07
模式原理优点限制
upmap
（推荐）		直接改写 PG→OSD 映射表迁移量最小、粒度最细、不改 crush map需要客户端 ≥ Luminous；映射表条目过多（>10万）时有性能开销
crush-compat通过调 crush weight 的"兼容权重"实现兼容所有版本客户端粒度粗（只能按 OSD 整体调），迁移量比 upmap 大
read只生成计划不执行演练/审计用不会真的均衡
none关闭——
生产建议：① 集群稳定后开启 balancer on + mode upmap + 时间窗（业务低峰）；② max_misplaced 设 0.05，避免一次迁移太多；③ 扩容后先让 backfill 跑完再开 balancer，否则两套迁移逻辑叠加会把带宽吃光；④ 每周看一次 balancer status 确认它在正常工作。

4.5 pg_num 规划与调整

经验公式： 总 PG 数 ≈ (OSD 总数 × 100) / 副本数（replicated），然后向上取到最近的 2 的幂。
例：30 个 OSD、3 副本 → 30×100/3 = 1000 → 取 1024。
但要注意：这是"整个集群"的 PG 预算，需要按各 pool 的数据量占比分摊到每个 pool。
场景每 OSD 目标 PG说明
小集群（< 10 OSD）~100PG 太少会导致数据分布粒度粗、迁移单位过大
中等（10~100 OSD）~100标准值
大集群（> 100 OSD）100~200PG 过多会增加 CPU/内存开销与 peering 风暴风险
EC 池可按数据量折算EC 池的 PG 数可单独设，不必与副本池一致
 
# 自动扩缩容（Pacific+ 推荐，默认开启）
ceph osd pool set <pool> pg_autoscale_mode on        # on / off / warn
ceph osd pool autoscale-status                       # 看建议值与实际值
ceph config set global mon_target_pg_per_osd 100     # 全局目标值

# 手动调整（★ 金科玉律：一次只翻倍的一半，分批加）
ceph osd pool set <pool> pg_num 1024     # 先改 pg_num（拆分 PG）
ceph osd pool set <pool> pgp_num 1024    # 再改 pgp_num（才真正开始迁移）
# 观察：ceph -s 直到 active+clean 后再进行下一批

# 缩减 PG（Nautilus+ 支持，但风险较高）
ceph osd pool set <pool> pg_num 512 --yes-i-really-mean-it
PG 调整的三大坑：
① 只改 pg_num 不改 pgp_num → PG 拆了但不迁移，等于没做；
② 一次加太多（如 256 → 4096）→ 瞬间触发海量 backfill + peering，集群直接不可用。正确做法：256→384→512→768→1024，每步等 clean；
③ 在集群已经不健康时调 → 叠加风险。必须等 HEALTH_OK 再动。

PG 卡死（incomplete / 长期 peering）专项处理

# 1. 看 PG 详情，确认哪些 OSD 参与
ceph pg 3.4f query | jq '{state, up: .up, acting: .acting, blocked: .blocked}'

# 2. 找出该 PG 所有副本所在的 OSD，逐个检查是否 up
ceph pg 3.4f query | jq '.acting[]' | xargs -I{} ceph osd find {}

# 3. 列出各副本上有哪些对象（确认权威副本：对象最全的那个）
for osd in 5 12 31; do
  echo "--- osd.$osd ---"
  ceph-objectstore-tool --data-path /var/lib/ceph/osd/ceph-$osd --type bluestore \
     --pgid 3.4f --op list | wc -l
done

# 4. 若确认某副本是权威的，用它覆盖其他副本（★ 高危，先备份）
ceph-objectstore-tool --data-path /var/lib/ceph/osd/ceph-5 --type bluestore \
   --pgid 3.4f --op export --file /tmp/pg3.4f.export
ceph-objectstore-tool --data-path /var/lib/ceph/osd/ceph-12 --type bluestore \
   --pgid 3.4f --op import --file /tmp/pg3.4f.export

# 5. 全部丢失时的最后手段（会丢数据！必须业务方签字）
ceph pg 3.4f mark_unfound_lost delete     # 或 revert（回滚到旧版本）
incomplete 处理铁律：操作前必须备份相关 OSD 的 PG 数据；mark_unfound_lost 是不可逆的数据删除，执行前必须确认没有别的副本能恢复（把所有 down 的 OSD 都尝试拉起来再看一遍）。

5扩容（加 OSD / 加节点）

5.1 三种扩容场景与决策

场景 A：加 OSD

现有节点还有空盘位/空槽位。
影响：触发 backfill，数据向新盘迁移。
关键：控制迁移速率。

场景 B：加节点

整台机器加入（含若干 OSD）。
影响：迁移量最大，等于给每个 PG 重新洗牌。
关键：确认 crush bucket 位置正确。

场景 C：换大盘（原地扩）

把 4T 换成 8T。
影响：需先 out 旧盘再 in 新盘，迁移量大。
关键：容量必须够放得下。

扩容前必做的三项检查

# 1. 当前是否健康 —— 不健康绝对不要扩
ceph health detail      # 必须 HEALTH_OK 或至少没有 ERR
ceph osd df             # 确认没有 OSD 超过 80%

# 2. 剩余容量是否够（★ 最重要）
# 规则：扩容期间任一 OSD 使用率都不能超过 nearfull(85%)，
#       且集群需保留 ≥ 10% 的空闲空间作为迁移缓冲
ceph df | head

# 3. 当前有无进行中的迁移
ceph -s | grep -i recovery
ceph pg stat
血泪教训：在集群已用 85%+ 时扩容，backfill 会把剩余空间吃光导致 full → 整个集群只读。正确顺序是：先确保有足够空闲空间，再扩容。如果已经很满，应该先缩容（删数据）或临时降低副本数（ceph osd pool set <pool> size 2，仅应急且要评估风险）。

5.2 加 OSD 全流程（手动部署）

# ── ① 准备（在目标节点执行）─────────────────────────
lsblk -o NAME,SIZE,MODEL,SERIAL,WWN
ls -l /dev/disk/by-id/                      # ★ 用 by-id 路径，重启后不会变
# 确认是 SSD 还是 HDD（影响 crush device class）
cat /sys/block/sdX/queue/rotational         # 1=HDD  0=SSD

# ── ② 限流（★ 在扩容窗口内设置）────────────────────
ceph tell osd.* injectargs '--osd_max_backfills=1'
ceph tell osd.* injectargs '--osd_recovery_max_active=1'      # HDD 建议 1，SSD 可 3
ceph tell osd.* injectargs '--osd_recovery_sleep=0.1'         # HDD 0.1~0.5；SSD 0~0.05
ceph tell osd.* injectargs '--osd_recovery_op_priority=1'     # 低于业务(63)
ceph tell osd.* injectargs '--osd_recovery_max_single_start=1'

# ── ③ 创建 OSD ─────────────────────────────────────
# 方式一：单盘（HDD/SSD）
ceph-volume lvm create --data /dev/disk/by-id/wwn-0x50014ee...

# 方式二：db/wal 分离（推荐 HDD+NVMe 混闪）
ceph-volume lvm create --data /dev/sdd --block.db /dev/nvme0n1

# 方式三：批量（一次加多块盘）
ceph-volume lvm batch --yes /dev/sdd /dev/sde /dev/sdf \
   --db-devices /dev/nvme0n1 --wal-devices /dev/nvme1n1

# 方式四：精细控制 db/wal 大小
ceph-volume lvm create --data /dev/sdd --block.db vg_nvme/lv_db2 --block.db-size 40G

# ── ④ 归位到 host（★ 关键）─────────────────────────
ceph osd tree                               # 看新 OSD 现在在哪
ceph osd crush move osd.24 host=node-05     # 移到对应 host bucket
# 若集群按 rack 划分，还要确认 host 已在正确的 rack 下
ceph osd crush move node-05 rack=rack-01
# 检查 device class 是否正确
ceph osd crush rm-device-class osd.24       # 若需重设
ceph osd crush set-device-class ssd osd.24

# ── ⑤ 观察 ─────────────────────────────────────────
watch -n5 'ceph -s | tail -12'
ceph -s    # 等待 pgs 全部 active+clean，io.recovery 归零
一次加几块盘合适？经验值：HDD 集群一次不超过总盘数的 5%（如 60 盘一次加 3 块），SSD 集群可以放宽到 10%。加完后等 active+clean 再继续下一批。批量加盘（一次 12 块）在容量充裕时也常见，但必须提前限速并在业务低峰做。

5.3 加节点（整体流程）

# ── 1. 新节点系统准备 ───────────────────────────────
# 同部署手册：关闭 SELinux/防火墙、NTP、内核参数、hosts 解析、免密 SSH

# ── 2. 安装 ceph 包（版本必须与集群一致！）──────────
ceph -v                                    # 现有集群版本
yum install -y ceph-19.2.0-0.el9.x86_64    # 或 apt，版本要对齐

# ── 3. 同步配置与 keyring ───────────────────────────
scp /etc/ceph/ceph.conf node-06:/etc/ceph/
scp /etc/ceph/ceph.client.admin.keyring node-06:/etc/ceph/
scp /var/lib/ceph/bootstrap-osd/ceph.keyring node-06:/var/lib/ceph/bootstrap-osd/

# ── 4. 创建 host bucket 并放到正确位置 ──────────────
ceph osd crush add-bucket node-06 host
ceph osd crush move node-06 rack=rack-02    # 或 root=default
# 若用 rack 级故障域，务必确认 rack 分布合理（不要所有机器挤一个 rack）

# ── 5. 批量创建 OSD ─────────────────────────────────
ceph-volume lvm batch --yes /dev/sdb /dev/sdc /dev/sdd /dev/sde \
    --db-devices /dev/nvme0n1
# ceph-volume 会自动把 OSD 放在本机 hostname 对应的 bucket 下（前提：hostname 与 bucket 名一致）

# ── 6. 校验 ─────────────────────────────────────────
ceph osd tree | grep -A20 node-06

ceph -s
hostname 一致性：ceph-volume 默认把新 OSD 挂到名为 $(hostname -s) 的 bucket 下。如果 hostname 是 node-06 但你建的 bucket 叫 node06，OSD 就会被放到一个自动创建的孤立 bucket 里，故障域静默失效。这是加节点最常见的隐蔽错误 —— 加完务必 ceph osd tree 看一眼。

5.5 容量告警与 full 急救

三道水位线（可调）：
mon_osd_nearfull_ratio = 0.85　→ 告警 nearfull
mon_osd_backfillfull_ratio = 0.90　→ OSD 拒绝接收 backfill（PG 卡在 backfill_wait）
mon_osd_full_ratio = 0.95　→ 集群只读，所有写入挂起 
# 紧急处理顺序（按风险从低到高）
# 1. 立刻确认到底谁满了
ceph osd df | sort -k14 -nr | head

# 2. 快速释放空间（安全）
rbd snap purge <pool>/<image>            # 删快照（先确认业务不需要！）
radosgw-admin gc process                 # RGW 触发垃圾回收
ceph osd pool set <pool> compression_mode aggressive   # 应急压缩（会消耗 CPU）

# 3. 降低副本数（★ 有风险，但救命最快）
ceph osd pool set <pool> size 2          # 3副本→2副本，立即省 1/3 空间
# 风险：此后再坏一块盘就有丢数据风险，必须尽快补容量并改回 3

# 4. 临时抬高水位线（★ 拆报警器，不到万不得已别做，且必须同步扩容）
ceph tell mon.* injectargs '--mon_osd_full_ratio=0.97'
# 做完后务必改回，并优先安排扩容

# 5. 真正的解决：加盘 / 删数据 / 迁移到外部存储
预防优于急救：把告警阈值设在业务侧而非 Ceph 侧 —— 当 pool 使用率达到 70% 就触发工单扩容。因为 Ceph 从 85% 到 95%（只读）在写入密集场景下可能只有几小时。

6缩容、摘盘与换盘

6.1 安全摘除单个 OSD（标准七步）

# ── 完整命令序列（以 osd.12 为例）──────────────────
# 0. 前置：确认剩余容量够（★ 这一步省略过的人后来都后悔了）
ceph osd df | sort -k14 -nr | head        # 最高使用率不能超过 80%

# 1. 标记 out（数据开始迁走）
ceph osd out 12
watch -n10 'ceph -s | tail -8'            # 观察 recovery 进度

# 2. ★ 等待完全 clean（可能几小时到几天）
while ! ceph -s | grep -q 'HEALTH_OK'; do sleep 60; done
ceph osd safe-to-destroy 12               # 4 的检查可以提前做

# 3. 停进程
systemctl stop ceph-osd@12
systemctl disable ceph-osd@12

# 4. ★ 安全检查（必须先 stop 才能查）
ceph osd safe-to-destroy 12
# 期望输出：OSD(s) 12 are safe to destroy without reducing data durability.
# 若输出 "... are still needed"，STOP！回去查原因

# 5. 清除（一条命令搞定 out + crush remove + auth del）
ceph osd purge 12 --yes-i-really-mean-it
# 或分步（老版本）：
#   ceph osd crush remove osd.12
#   ceph auth del osd.12
#   ceph osd rm 12

# 6. 清理 LVM 与磁盘（在 OSD 所在节点执行）
ceph-volume lvm list | grep -A5 'osd.12'      # 确认 LV 名称
lvremove -f vg_xxx/lv_xxx
vgremove vg_xxx
pvremove /dev/sdX
wipefs -a /dev/sdX                        # ★ 清掉签名，否则下次用这块盘会报已存在

# 7. 验证
ceph osd tree
ceph -s
ceph osd df tree

6.2 摘除整个节点

# 1. 先把该节点上所有 OSD 一起 out（比逐个 out 快，且只触发一轮迁移）
ceph osd out $(ceph osd ls-tree node-06 | tr '\n' ' ')
# 或者（更稳妥，逐盘）
for i in $(ceph osd ls-tree node-06); do ceph osd out $i; done

# 2. 等待 active+clean
watch -n30 'ceph -s'

# 3. 逐个 stop + safe-to-destroy + purge
for i in $(ceph osd ls-tree node-06); do
  ssh node-06 "systemctl stop ceph-osd@$i"
  ceph osd safe-to-destroy $i || { echo "osd.$i NOT safe, abort"; break; }
  ceph osd purge $i --yes-i-really-mean-it
done

# 4. 移除 host bucket
ceph osd crush rm node-06
# 5. 若该节点还跑了 mon/mgr/mds/rgw，先迁走/删除对应服务
ceph mon remove node-06
# 6. 清理服务与包（可选）
ssh node-06 "yum remove -y ceph*; rm -rf /var/lib/ceph/*"

6.3 换盘（故障盘替换）

方案 A：保留 OSD ID（推荐）

新盘用同一个 OSD 编号，迁移量 = 一块盘的数据量，影响最小。
适用：盘坏了但能识别、或已安全 out。

方案 B：不保留 ID（新建 OSD）

老 ID purge，新盘拿新 ID。会触发更大规模的 rebalance（因为 CRUSH 树变了）。
适用：老 ID 已无法恢复、或顺带调整容量。

# ── 方案 A：保留 OSD ID 换盘 ───────────────────────
# 1. 确认盘确实坏了
ceph osd perf | grep -w 12 ; dmesg | grep -i 'sdX' ; smartctl -a /dev/sdX

# 2. 标记 out 并等数据迁走（坏盘可能迁不动，见下方"打不动"处理）
ceph osd out 12 ; watch -n10 'ceph -s'

# 3. 停进程（注意：如果盘已经完全不可读，这步可能卡住）
systemctl stop ceph-osd@12
# 若 stop 卡死：systemctl kill -s KILL ceph-osd@12

# 4. 安全确认
ceph osd safe-to-destroy 12

# 5. 清除元数据但保留 ID
ceph osd destroy 12 --yes-i-really-mean-it      # 注意：是 destroy 不是 purge（purge 会连 ID 一起删）
ceph auth del osd.12

# 6. 物理换盘后，用同一个 ID 重建（在目标节点执行）
ceph-volume lvm create --osd-id 12 --data /dev/disk/by-id/wwn-0x...
# 若还有独立的 db/wal，需要重新指定：
ceph-volume lvm create --osd-id 12 --data /dev/sdd --block.db vg_nvme/lv_db12

# 7. 开机自启
systemctl enable --now ceph-osd@12

# 8. 若 OSD 启动时报 "osd.12 already exists" 或 crush 里还有残留
ceph osd crush rm osd.12
ceph osd crush move osd.12 host=node-05
# ── 方案 B：全新 OSD ───────────────────────────────
ceph osd out 12
# 等 clean
ceph osd safe-to-destroy 12
ceph osd purge 12 --yes-i-really-mean-it
# 清 LV / wipefs（见 6.1 第 6 步）
# 换盘后
ceph-volume lvm create --data /dev/disk/by-id/wwn-0x...
ceph osd crush move osd.NEW host=node-05
"数据迁不动"怎么办：坏盘可能让 PG 卡住导致 backfill 无法完成。此时 ceph -s 会有 PG 长期 degraded。
处理：① 确认 min_size 是否满足（ceph osd pool ls detail）；② 若该 OSD 已完全不可用且其他副本齐全，用 ceph osd destroy + ceph osd crush remove 强制剔除，数据由剩余副本重建；③ 若 该 OSD 上有唯一副本（比如 2 副本且另一块也坏了），只能从备份恢复 —— 这就是为什么副本数不能低于 3。

6.4 缩容容量红线（动手前必算）

#!/bin/bash
# check_shrink.sh —— 缩容前容量检查（强烈建议纳入变更流程）
# 用法: ./check_shrink.sh "12 13 14"

TARGET_OSDS="$1"
TOTAL_RAW=$(ceph df --format=json | jq '.stats.total_bytes')
USED_RAW=$(ceph df --format=json | jq '.stats.total_used_bytes')
echo "集群: 总 $((TOTAL_RAW/1024**4)) TiB / 已用 $((USED_RAW/1024**4)) TiB \
( $((USED_RAW*100/TOTAL_RAW))% )"

REMOVE_BYTES=0
for o in $TARGET_OSDS; do
  B=$(ceph osd df --format=json | jq ".nodes[]|select(.id==$o)|.kb" )
  REMOVE_BYTES=$((REMOVE_BYTES + B*1024))
done
echo "拟摘除 OSD: $TARGET_OSDS"
echo "将释放容量: $((REMOVE_BYTES/1024**4)) TiB"

NEW_TOTAL=$((TOTAL_RAW - REMOVE_BYTES))
NEW_PCT=$((USED_RAW*100/NEW_TOTAL))
echo "摘除后: 总 $((NEW_TOTAL/1024**4)) TiB, 使用率将变为 ${NEW_PCT}%"

if [ $NEW_PCT -gt 85 ]; then
  echo "❌ 危险！使用率将超过 85%（nearfull），禁止执行缩容"
  exit 1
elif [ $NEW_PCT -gt 75 ]; then
  echo "⚠️  警告：使用率将超过 75%，建议先清理数据或分批缩容"
else
  echo "✅ 容量安全，可以执行"
fi
缩容三原则：① 摘除后集群使用率 必须 < 75%（留出缓冲）；② 一次只摘一个节点或一批 OSD，等 clean 再进行下一批；③ 缩容过程中不要同时做其他变更（扩容、升级、调 PG）。

7.2 一键巡检脚本（可直接落地到 crontab）

#!/bin/bash
# ceph_healthcheck.sh —— Ceph 日常巡检（Squid/Tentacle）
# 用法: bash ceph_healthcheck.sh  |  crontab: 0 9 * * * /opt/ceph_healthcheck.sh | mail -s "Ceph日报" ops@xx.com

RED='\033[0;31m'; YEL='\033[0;33m'; GRN='\033[0;32m'; NC='\033[0m'
WARN=0
say()  { echo -e "$1"; }
bad()  { echo -e "${RED}[FAIL]${NC} $1"; WARN=1; }
warn() { echo -e "${YEL}[WARN]${NC} $1"; }
ok()   { echo -e "${GRN}[ OK ]${NC} $1"; }

echo "════════ Ceph 巡检报告 $(date '+%F %T') ════════"

# 1. 健康状态
H=$(ceph health 2>/dev/null)
echo "── 1. 集群健康 ──"
if [ "$H" == "HEALTH_OK" ]; then ok "$H"; else
  bad "$H"; ceph health detail | head -20; fi

# 2. OSD up/in
echo "── 2. OSD 状态 ──"
STAT=$(ceph osd stat 2>/dev/null)
echo "$STAT"
UP=$(echo "$STAT" | grep -oP '\d+(?= up)'); IN=$(echo "$STAT" | grep -oP '\d+(?= in)')
[ "$UP" == "$IN" ] && ok "up=$UP in=$IN 一致" || bad "up=$UP in=$IN 不一致，有 OSD 被 out"

# 3. PG
echo "── 3. PG 状态 ──"
ceph pg stat | sed 's/^/   /'
NOTCLEAN=$(ceph pg stat --format=json 2>/dev/null | jq -r '.num_pgs - .pgs_by_state[]? | select(.state_name=="active+clean") | .count' 2>/dev/null)
ceph pg stat | grep -qE 'degraded|inconsistent|stale|incomplete|down' && bad "存在异常 PG" || ok "PG 全部 active+clean"

# 4. 容量
echo "── 4. 容量水位 ──"
ceph df | head -8
ceph osd df --format=json | jq -r '.nodes[]|select(.type=="osd")|"\(.name) \(.utilization) \(.var)"' | \
  sort -k3 -nr | head -5 | while read n u v; do
    p=${u%.*}
    if   [ "$p" -ge 85 ]; then bad "$n 使用率 ${u}% VAR=$v"
    elif [ "$p" -ge 75 ]; then warn "$n 使用率 ${u}% VAR=$v"
    fi
  done

# 5. 慢盘
echo "── 5. 慢 OSD TOP5（commit/apply 延迟 ms）──"
ceph osd perf | sort -k3 -nr | head -6

# 6. MON
echo "── 6. MON ──"
ceph mon stat
ceph quorum_status --format=json | jq -r '"   leader=\(.quorum_leader_name) quorum=\(.quorum_names|join(","))"'

# 7. MGR
echo "── 7. MGR ──"
ceph mgr stat | sed 's/^/   /'

# 8. 版本一致性
echo "── 8. 版本一致性 ──"
ceph versions | sed 's/^/   /'

# 9. 网络错误（本机）
echo "── 9. 网卡错误计数 ──"
for i in $(ls /sys/class/net | grep -Ev '^(lo|docker|veth|virbr)'); do
  e=$(ethtool -S $i 2>/dev/null | grep -E 'rx_errors|tx_errors|rx_dropped' | awk '{s+=$2} END{print s}')
  [ "${e:-0}" -gt 0 ] && warn "$i 存在错误包: $e" || ok "$i 无错误"
done

echo "════════ 巡检结束 ════════"
exit $WARN

7.3 集群"健康打分"简易模型

给集群打分的快速方法（满分 100，用于向上汇报或变更前后对比）：
健康状态 30 分：OK=30，WARN=15，ERR=0
容量水位 20 分：最高 OSD <60% = 20，60~75% = 12，75~85% = 5，>85% = 0
均衡度 20 分：VAR 标准差 <0.08 = 20，<0.15 = 12，<0.25 = 5，更大 = 0
性能 20 分：P99 延迟达标 = 20，超 2 倍 = 10，超 5 倍 = 0

9变更红线：这些事绝对不能做

🚫 高危操作（必须有方案 + 审批 + 备份）

① ceph osd lost —— 强制宣告数据丢失
② mark_unfound_lost —— 不可逆删除
③ 批量重启多个 OSD（未 set noout）
④ 上调 full_ratio 而不扩容
⑤ rbd feature disable 后未验证
⑥ 直接删除 /var/lib/ceph/osd/* 目录
⑦ 在生产集群上跑 fio 打满压测

✅ 变更标准动作（Checklist）

① 变更前：ceph health detail 确认健康 + 记录基线（ceph -s > /tmp/before.txt）
② ceph osd set noout（涉及 OSD 停机时）
③ 一次只改一个变量，改完观察 10 分钟
④ 参数用 injectargs 先验证，再 ceph config set 持久化
⑤ 变更后：对比基线 + 更新运维文档
⑥ 全程保留回滚方案

三个被反复验证的"反直觉"经验：
1. 集群规模越大，越要控制单次变更范围。100 个 OSD 时重启 3 个没事，重启 30 个就是灾难。
2. 告警静音不等于问题解决。把 mon_osd_nearfull_ratio 从 0.85 调到 0.95 只需要一条命令，但代价是失去扩容窗口。
3. Ceph 很少"自己坏"，绝大多数故障是硬件（盘/网/内存）或人的行为。排查时先怀疑这两者。
