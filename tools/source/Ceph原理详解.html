0写在前面：怎么读这份文档

Ceph 难学，不是因为它概念多，而是因为它的概念分层很明显：底层的 RADOS 是一套完整的分布式对象存储，上层的 RBD / RGW / CephFS 只是三种"客户端"。很多人一上来就看 RBD 怎么用，结果遇到 ceph -s 报 PG 异常就懵了 —— 因为你跳过的是整个地基。

Ceph 一句话定义

Ceph 是一个统一的、分布式的、软件定义存储系统。它在同一套集群上同时提供三种存储能力：

  • 块存储 RBD —— 像云硬盘一样挂给虚拟机 / 数据库 / Kubernetes PV
  • 对象存储 RGW —— 兼容 S3 / Swift 协议，用于备份、归档、AI 数据集、静态资源
  • 文件存储 CephFS —— POSIX 兼容的共享文件系统，用于 HPC、CI/CD、共享目录

这三种能力共用同一个底层存储池。这是它跟"三套独立存储系统"的本质区别。

1Ceph 到底解决什么问题

1.1 传统存储的两个死穴

在 Ceph 出现之前，企业存储大致两条路，但都有硬伤：

方案工作方式死穴
传统 SAN/NAS 阵列双控制器 + 专用硬盘柜，控制器里跑 RAID，对外暴露 LUN / NFS纵向扩展天花板：容量和性能受限于那两个控制器；厂商锁定：扩容只能买同品牌盘柜；贵：每 GB 成本高一个数量级
早期分布式文件系统
（如 HDFS / GlusterFS / Lustre）		数据节点 + 中心元数据节点（NameNode / MDS）元数据单点：NameNode 挂了整个集群不可写；元数据瓶颈：海量小文件时元数据节点先被打爆

Ceph 的答案很直接：把元数据也分布式掉，让"数据在哪"不再需要查表，而是"算"出来。

1.2 Ceph 的四个设计目标

① 无单点故障（No SPOF）

MON 用 Paxos 组 quorum（奇数个，通常 3 或 5）；数据多副本或 EC 编码；任何组件都可以有副本。没有"主控制器"这种东西。

② 线性可扩展（Scalable）

从 3 台到 3000 台用同一套代码。扩容 = 加节点 = 数据自动迁移一部分过去，无需停机、无需手动分配。

③ 自愈与自管理（Autonomic）

硬盘坏了自动标记 out、自动在其他 OSD 上重建副本、重建完再自动回到均衡。运维要做的只是"把坏盘拔了换新的"。

④ 商用硬件 + 开源（Commodity）

不依赖专用硬件，普通 x86 服务器 + 万兆网卡 + SATA/SAS/NVMe 即可。软件定义，无厂商锁定。

2.2 五张 Map：Ceph 的"集群真相"

Ceph 集群没有数据库，它的"状态"就是 MON 里维护的这几张 Map。理解它们，就理解了 ceph -s 输出的每一行。

2.3 MON 的 Paxos 与 quorum

MON 为什么要奇数个？因为 MON 之间用 Paxos 算法对 Map 的每一次修改达成共识，而 Paxos 要求多数派（quorum）。

3 个 MON：需要 2 个存活 → 可容忍 1 台故障
5 个 MON：需要 3 个存活 → 可容忍 2 台故障
4 个 MON：需要 3 个存活 → 也只能容忍 1 台故障，所以偶数个是浪费，永远用奇数。
生产建议：小规模集群 3 个 MON 足够；超过 50 个 OSD 或者跨机柜部署，建议 5 个 MON（放在不同机柜/故障域）。不要把 MON 和 OSD 混部在同一台重负载机器上——MON 对延迟敏感，OSD 重建时的 I/O 风暴会拖垮 MON，进而导致集群"假死"。

3数据寻址三部曲：File → Object → PG → OSD

这是全篇最重要的一章。Ceph 为什么能"算"出数据在哪？因为寻址是纯计算，没有任何查表。

3.1 第一步：File → Object（切条带）

一个 1GB 的文件不会作为一个整体存。Ceph 会把它切成若干对象（Object）：对象名 = 镜像名或 inode 号 + 序号，默认对象大小 4MB（RBD 可通过 --object-size 调整）。

# RBD 镜像 "vm-disk-01" 的一个文件，切成 4MB 对象后：
rbd_data.1a3f2b8c4567.0000000000000000   ← 第 0 个对象（offset 0 ~ 4MB）
rbd_data.1a3f2b8c4567.0000000000000001   ← 第 1 个对象（offset 4MB ~ 8MB）
...
rbd_data.1a3f2b8c4567.00000000000000ff   ← 第 255 个对象（1GB / 4MB = 256 个）
为什么要切？① 并行：256 个对象散落在几百块盘上，一次大文件读写变成几百个并发小 I/O，吞吐直接叠加；② 均衡：小粒度才可能均匀；③ 恢复粒度可控：坏盘后重传的是一个个 4MB 对象，而不是整个 1GB 文件。

3.2 第二步：Object → PG（为什么要引入 PG）

如果直接把几千万个 Object 映射到几千个 OSD 上，会有两个灾难：

  • 元数据爆炸：OSDMap 要记录"每个对象在哪"，几千万条记录根本存不下、也同步不动；
  • 无法做一致性：每个对象独立管理副本状态，几千万个状态机无法维护。

Ceph 的解法是引入中间层 PG（Placement Group，归置组）：Object 先哈希到 PG，PG 再通过 CRUSH 映射到 OSD。PG 是 Ceph 的一致性单元、迁移单元、均衡单元。

# 计算方式（概念，非真实代码）
hash(object_name)  →  得到一个 32 位整数
pg_id = hash(object_name) & (pg_num - 1)     # 按 pg_num 取模
# 加上 pool 前缀，形成最终的 PG 标识：
pgid  = "{pool_id}.{pg_id}"                   # 例如  2.1f
PG 的本质：PG 是"一组对象的集合"，也是"一组 OSD 的集合"的中间桥梁。
· 对上（对象）：所有 hash 到同一个 PG 的对象，一定存放在同一组 OSD 上。
· 对下（OSD）：一个 PG 会被 CRUSH 分配到 N 个 OSD（N = 副本数 或 k+m）。
所以 Ceph 只需要维护 PG 数量级（几千~几万）的状态，而不是对象数量级（几十亿）。这就是 PG 存在的意义 —— 把规模降下来。

3.3 第三步：PG → OSD（CRUSH）

最后一步由 CRUSH 完成：输入 (pgid, crush_rule, cluster_map)，输出一组 OSD 列表。这一章先知道结论，第 4 章展开算法。

3.4 完整寻址图

这就是 Ceph 可扩展的秘密。客户端不依赖任何中心节点做寻址。加机器 → CRUSH Map 变大一点（几 MB）→ 客户端拉一次新 Map → 继续本地计算。MON 不参与数据路径，所以哪怕集群有 5000 个 OSD、10 万个客户端，MON 的负载也不会线性增长。

3.5 up set 与 acting set 的区别

这两个集合在正常状态下相同，但在数据迁移期间会分叉 —— 这是理解 PG 状态的关键：

  • Acting Set：CRUSH 算出来的、应该持有这个 PG 的 OSD 列表（权威答案）。
  • Up Set：当前实际在提供服务的 OSD 列表。当 acting 中的某个 OSD 还没完成数据回填时，Ceph 会临时保留老 OSD 在 up set 里继续服务，直到新 OSD 追上数据。

4CRUSH 算法详解

CRUSH = Controlled Replication Under Scalable Hashing（可控的、可扩展的、基于哈希的复制）。它解决三件事：

① 数据放哪

输入 PG 编号，输出 N 个 OSD。

② 遵守故障域

3 副本必须落在 3 个不同主机/机柜/机房，不能全挤在一台机器上。

③ 变化时影响最小

加一块盘，只有约 (新增容量/总容量) 比例的数据需要搬迁，而不是全量重排。

4.1 CRUSH Map：一棵描述机房拓扑的树

CRUSH Map 的核心是一棵层级树。叶子是 OSD（真实设备），中间节点是 bucket（逻辑容器）。

4.2 选择算法：straw2（抽签）

CRUSH 在每一层选子节点时，用的是 straw2 算法。思想极其朴素但效果很好：

  1. 对每个候选 OSD，用 hash(pg_id, osd_id, 尝试次数r) 生成一个 0~1 之间的随机数；
  2. 把这个随机数按 OSD 权重做缩放：抽签长度 = 随机数 ^ (1 / weight)，权重越大抽签越长；
  3. 选"抽签最长"的那个 OSD。
straw2 的两个关键性质：
① 权重成比例：weight=4 的盘理论上拿到的数据量是 weight=1 的盘的 4 倍。
② 变动影响最小：某个 OSD 的权重变化，只会影响它自己那份数据，其他 OSD 之间的抽签结果完全不受影响（这是相对于老 straw 算法的改进）。所以加一块盘，只会有约 (新盘容量/总容量) 比例的数据迁移过来 —— 这就是 Ceph 能做到"平滑扩容"的数学基础。

4.3 CRUSH Rule：把策略写进集群

Rule 定义了"怎么选、选几个、按什么故障域避让"。看一个真实的 rule：

# 查看当前集群的 CRUSH rule
$ ceph osd crush rule dump replicated_rule

{
  "rule_id": 0,
  "rule_name": "replicated_rule",
  "type": 1,                       # 1 = 副本型, 3 = 纠删码型
  "steps": [
    { "op": "take",     "item": -1, "item_name": "default" },   # 从 root=default 开始
    { "op": "chooseleaf_firstn", "num": 0, "type": "host" },    # 选 3 个不同的 host 下的叶子(osd)
    { "op": "emit" }
  ]
}

"chooseleaf_firstn, num=0, type=host" 的意思是：选 N 个（N=池的副本数）不同 host 下的 OSD。如果某个 host 已经被选过，就跳过重抽，这就是故障域的实现方式。

实战：为 SSD 和 HDD 建立两套 rule（分级存储） 
# 1. 按设备类型自动分类（需要 OSD 上报 device_class）
$ ceph osd crush class ls
["hdd", "nvme", "ssd"]

# 2. 创建只使用 SSD 的 rule
$ ceph osd crush rule create-replicated ssd_rule default host ssd

# 3. 创建只使用 HDD 的 rule，且故障域是机柜
$ ceph osd crush rule create-replicated hdd_rack_rule default rack hdd

# 4. 给池指定 rule
$ ceph osd pool set my-fast-pool crush_rule ssd_rule

5一致性：一次写入的完整旅程

本章回答三个问题：Ceph 是强一致还是最终一致？写操作到底走了几跳？机器坏了以后数据怎么保证不丢？

5.1 结论先行

Ceph 是强一致的（CP 系统）。对同一个对象的写入，只有在所有副本都持久化成功后，才向客户端返回 ack。因此任何一次成功的写，之后的读一定能读到。
代价是：写入延迟 = 最慢那个副本的延迟（不是平均，是最慢）。这也是为什么调优时特别关注"长尾延迟"和网络 P99。

5.2 PG 是一致性单元

每个 PG 有自己的一套状态机，包含：

  • Acting Set：当前持有该 PG 的 OSD 列表，第一个是 Primary。
  • PGLog：这个 PG 最近的操作日志（默认保留 3000 条，osd_pg_log_dups_tracked 等参数可调）。它是故障恢复时判断"哪些对象不一致"的依据，避免了全量扫描。
  • last_update / last_complete：已提交的最大版本、已完全同步的最大版本。
  • Peering 状态：PG 是否完成了副本间的协商。

5.3 Primary 的职责

客户端永远只和 Primary OSD 通信（读和写都是）。Primary 负责：

  • 把写请求串行化（同一个对象的并发写在 Primary 上排队，保证顺序）；
  • 把写请求扇出给所有 Replica；
  • 等所有副本 ack 后再回复客户端；
  • 维护 PGLog，驱动恢复流程。

5.5 EC（纠删码）池的写入有什么不同

副本池每个副本存完整数据；EC 池每个分片存编码后的数据块或校验块。写入时：

  • Primary 需要先收齐完整的写请求数据（如果是部分写，需要先读出旧数据块和校验块重新编码，这就是 EC 小 I/O 慢的原因）；
  • 编码后切成 k 个数据块 + m 个校验块，发给 k+m 个 OSD；
  • 只需 k 个分片 ack 即可返回（不需要等 m 个校验块，因为它们可由数据块重算）。

MON 确认 downmon_osd_down_out_interval = 600sOSD 被标记 down 后，默认 10 分钟才自动标记 out 并触发数据重建
为什么默认 10 分钟才 out？因为换一块盘、重启一台机器通常几分钟内完成。如果 down 30 秒就开始大规模重建，一次简单的重启就会引发 PB 级数据搬迁，这是灾难。
生产建议：不要随意调小这个参数。临时停机维护前，改用 ceph osd set noout 显式禁止 out，维护完再 unset noout。

6自愈：Recovery 与 Backfill

数据怕的不是"坏"，而是"坏了没人管"。Ceph 的自愈分两种机制，很多人搞混，这里彻底讲清。

6.1 Recovery vs Backfill：本质区别

机制适用场景怎么找出缺失数据代价
Recovery
（恢复）		OSD 短暂离线后又回来了，只缺"离线期间新增/修改的少量对象"查 PGLog：对比各副本的 PGLog，精确定位到具体哪几个对象版本落后，只传这些对象极小。秒级~分钟级完成，几乎不影响业务
Backfill
（回填）		新 OSD 加入、OSD 被 out 后数据迁走、PG 数量调整 —— 需要全量搬一个 PG 的数据扫描整个 PG 的对象列表，把缺失对象逐个传过去大。会占用大量网络和磁盘 I/O，必须限速
一句话记忆：Recovery 是"补作业"（只补缺的那几页），Backfill 是"抄整本书"。
触发条件：Ceph 会先尝试 recovery；如果某个 OSD 缺失的数据太多、PGLog 已经覆盖不到（日志被截断），或者这个 OSD 根本就是全新的，就升级为 backfill。

6.4 Scrub：对抗"静默数据损坏"

7数据均衡原理

"为什么我的 12 块盘，有的用了 92%，有的才 71%？" —— 这是 Ceph 运维最高频的问题。本章把这个问题的根因、度量方法、治理手段讲透。

7.1 先分清两个"均衡"

PG 均衡（PG Count Balance）

每个 OSD 上承载的 PG 数量是否接近。CRUSH 是按 PG 分布的，它只保证"PG 数按权重成比例"，不知道每个 PG 里存了多少数据。

→ balancer 默认优化的就是这个。

容量均衡（Utilization Balance）

每个 OSD 的实际使用率（%）是否接近。这是你真正关心的 —— 集群能不能继续写，取决于最满的那块盘。

→ 需要 reweight-by-utilization 或 balancer 的 upmap-read 模式。

核心矛盾：CRUSH 保证的是"PG 数量均衡"，而 PG 里的数据量是随机且不均的 —— 有的 PG 对应的 RBD 镜像被写满了，有的 PG 只存了几个小对象。
结果就是：PG 数完全均衡，但使用率可以差 20 个百分点以上。这是设计使然，不是 bug。

7.2 为什么会不均衡：四个根因

#根因机理典型表现
1哈希本身的随机性PG → OSD 是随机抽样，不是精确装箱。OSD 数量越少，相对方差越大（统计学上 std ≈ √(总PG数/OSD数)）OSD 少于 50 个时，PG 数天然能差 ±10%
2PG 里的数据量不均PG 是等值单位，但每个 PG 实际存储量不同PG 数很齐，但 %USED 差很多 —— 最常见
3weight 与真实容量不符把 8TB 盘和 4TB 盘设成同样 weight=1.0，那 8TB 盘会先满混用不同容量盘时必现
4扩缩容的历史残留新加的 OSD 只接收"CRUSH 新算出来落在它头上"的 PG，老 OSD 不会主动把存量数据分给它扩容后新盘很空、老盘很满，长期不收敛

· 0.05 ~ 0.15：可接受
· > 0.15：明显不均衡，值得处理
· > 0.30：严重不均衡，集群容量被严重浪费

7.7 数据均衡的完整治理流程

一句话总结均衡治理：
日常靠 balancer + upmap 模式持续微调（低峰执行、自动收敛）；
应急靠 reweight-by-utilization 一次性大幅纠偏；
根治靠 正确的 weight 设置 + 合理的 PG 数量 + 避免混盘。

8PG 数量规划

PG 数量是部署时就要定对、事后很难改的关键参数。太多浪费资源，太少则数据无法均衡、恢复慢。

8.1 PG 太多 vs 太少的代价

情况代价表现
PG 太少
危险		① 数据分布粒度粗，CRUSH 再怎么优化也无法均衡；② 一个 PG 承载数据量过大，单盘故障恢复时间极长；③ 单 PG 的 peering 会锁住大量对象VAR 常年 >1.3；坏一块盘要恢复几十小时；ceph -s 长期 degraded
PG 太多
浪费		① 每个 OSD 上 PG 数多 → 内存占用大涨（每 PG 约几十 KB~几百 KB）；② peering 开销激增，OSD 重启后要花很久；③ scrub 开销放大；④ MON 的 OSDMap 变大OSD 进程 RSS 内存飙升；重启 OSD 后集群长时间 peering；ceph -s 里 pgs 数字巨大

8.2 计算方法

官方经验公式：
  每个 OSD 承载 100 ~ 200 个 PG（副本池，按"有效副本数折算后"的 PG 计）

计算步骤：
1. 总 PG 数（裸值） = (OSD 总数 × 200) / 副本数，然后向上取整到最接近的 2 的幂
2. 按每个池的容量占比分摊
3. 如果有多个池，用 "PG 总量预算" 分摊，而不是各自独立算 
# 计算示例：30 个 OSD，3 副本，计划 3 个池
# ① PG 总量预算
Total PGs = (30 × 200) / 3 = 2000  →  向上取到 2 的幂 → 2048

# ② 按池容量占比分摊（假设 rbd 占 60%，cephfs_data 占 30%，rgw 占 10%）
rbd池          : 2048 × 0.6 = 1229  →  取 1024（2 的幂，且不要超过预算太多）
cephfs_data池  : 2048 × 0.3 =  614  →  取 512
rgw_data池     : 2048 × 0.1 =  205  →  取 256

# ③ 校验：每 OSD 实际承载的 PG 数
#    注意：每个池的每个 PG，会被复制到 3 个 OSD 上
每 OSD 的 PG 数 = (1024 + 512 + 256) × 3 / 30 OSD = 179   ✅ 落在 100~200 区间内

# 也可以直接用官方在线计算器：https://ceph.io/pgcalc/

9BlueStore：Ceph 的存储引擎

从 Luminous(12.2) 开始，BlueStore 成为默认存储引擎，FileStore（基于 XFS + LevelDB）已被彻底淘汰。理解 BlueStore 是做性能调优的前提。

9.1 为什么 FileStore 被淘汰

问题FileStore 的做法BlueStore 的做法
双重写放大先写 Journal（独立 SSD），再写文件系统 → 一份数据写两遍元数据写 RocksDB，数据一次直接落裸设备
无法原子写依赖文件系统 journal 保证事务性，开销大RocksDB 事务保证元数据原子性，数据大块追加写
文件系统开销每次写要走 VFS → XFS → block layer，且有目录查找开销直接管理裸块设备，绕过文件系统
元数据性能对象属性存在文件的 xattr 里，读一次要多次 stat全部放 RocksDB（有序 KV），一次查询搞定
校验和缺失依赖文件系统，无端到端校验每份数据自带 checksum，deep scrub 才能真正防位翻转

#   内部再按 kv_ratio / meta_ratio 分给 RocksDB 和元数据
ceph config set osd bluestore_cache_kv_ratio 0.4      # RocksDB 占 40%
ceph config set osd bluestore_cache_meta_ratio 0.4    # 元数据占 40%
# 剩下 20% 给数据缓存
内存规划公式：如果一台机器有 N 个 OSD、物理内存 M GB，则 osd_memory_target ≤ (M - 系统预留 8GB) / N。
例：128GB 内存 + 12 个 OSD → 每 OSD 最多 (128-8)/12 = 10GB，保守取 8GB。
内存不足会导致 OSD OOM 被杀 → 触发大规模数据迁移 → 雪崩，这是生产事故的经典剧本。

10副本 vs 纠删码（EC）

10.1 核心取舍

维度多副本（Replicated）纠删码（Erasure Coding）
空间利用率3 副本 = 33.3%（1/3）4+2 = 66.7%；8+3 = 72.7%；8+2=80%
可靠性3 副本可容忍同时坏 2 个 OSDk+m 可容忍同时坏 m 个 OSD（4+2 容忍 2 个）
读性能快，直接读主副本正常情况一样快；降级读需要读 k 个分片重算 → 慢且吃网络
写性能好编码有 CPU 开销；部分写（partial write）需读-改-写，极慢
CPU 开销几乎无编码/解码需要 CPU（ISA-L 插件可硬件加速）
适用场景RBD（虚拟机、数据库）、CephFS、热数据RGW 对象存储、冷数据、备份归档、大文件
支持 RBD/CephFS✅⚠ RBD 仅支持 EC 池做 data pool（元数据池必须副本）；CephFS 支持但需 --allow-ec-overwrites

10.3 EC Profile 与创建

# 创建一个 4+2、故障域为 host 的 EC profile
ceph osd erasure-code-profile set ec42 \
    k=4 m=2 \
    crush-failure-domain=host \
    plugin=jerasure \
    technique=reed_sol_van \
    crush-device-class=hdd

# 常用参数说明
#   k/m              : 数据块 / 校验块数量
#   crush-failure-domain : host / rack / osd   —— 决定分片怎么散
#   plugin           : jerasure(通用) / isa(Intel CPU 加速) / lrc(局部重建) / clay(节省修复带宽)
#   technique        : reed_sol_van(默认) / cauchy / liberation 等
#   crush-device-class   : 限定使用 ssd / hdd / nvme

# 用 profile 创建 EC 池
ceph osd pool create ec-pool 512 512 erasure ec42

# ⚠ 关键：EC 池默认不支持部分写（overwrite），需要显式开启
ceph osd pool set ec-pool allow_ec_overwrites true
# 开启后才可用于 RBD(需配合副本元数据池) / CephFS

# 查看
ceph osd erasure-code-profile get ec42
ceph osd pool get ec-pool all
EC 池用于 RBD 的正确姿势：不能直接把 RBD 镜像放 EC 池。正确做法是分层：
ceph osd pool create rbd-ec-meta 64 64 replicated          # 元数据池：必须副本
ceph osd pool create rbd-ec-data 512 512 erasure ec42       # 数据池：EC
ceph osd pool set rbd-ec-data allow_ec_overwrites true
rbd create --size 100G --data-pool rbd-ec-data rbd-ec-meta/myimage
这样镜像的元数据放副本池（快），数据放 EC 池（省空间）。
插件选型建议：
· jerasure + reed_sol_van：通用默认，稳
· isa：Intel CPU 上编码速度快 2~3 倍（需 CPU 支持 SSE/AVX）
· lrc（Local Reconstruction Code）：牺牲一点空间，换故障修复时网络流量大幅下降。大集群强烈建议考虑
· clay：修复时流量和 I/O 都最优，但 CPU 开销略高

11三种存储接口

11.1 RBD（块存储）

把 RADOS 对象模拟成一块硬盘。不需要 MDS——"块的第 N 个扇区在哪个对象"这件事由 RBD 元数据（存在镜像头部对象里）自己算，纯计算。

  • 对象映射：LBA → 对象名 + 偏移，简单算术，客户端本地完成
  • 精简配置：写过的才分配空间（依赖 object-map 特性）
  • 快照/克隆：COW（写时复制），秒级完成，几乎不占空间
  • 两种访问方式：krbd（内核模块，性能好但功能受内核版本限制）vs librbd（用户态，功能全，K8s 和 QEMU 用这个）
# 常用操作
rbd create --size 100G --pool rbd --image-feature layering,exclusive-lock,object-map,fast-diff,deep-flatten vm-disk-01
rbd map rbd/vm-disk-01                 # 映射为 /dev/rbd0
rbd snap create rbd/vm-disk-01@snap1   # 秒级快照
rbd snap rollback rbd/vm-disk-01@snap1
rbd clone rbd/vm-disk-01@snap1 rbd/vm-disk-02   # 克隆
rbd flatten rbd/vm-disk-02             # 解除与父镜像的依赖

# 性能参数（客户端侧，写在 /etc/ceph/ceph.conf 的 [client] 段）
rbd_cache = true
rbd_cache_size = 32MB           # 用户态缓存大小
rbd_cache_max_dirty = 24MB      # 脏数据上限，超过开始回写
rbd_cache_writethrough_until_flush = true   # 保证数据安全（推荐 true）

11.2 RGW（对象存储）

一个无状态的 HTTP 网关，把 S3/Swift 请求翻译成 RADOS 操作。可以横向扩展 + 前面挂 LB（HAProxy/Nginx）。

  • 一个对象的构成：RGW 对象 = 1 个 head 对象 + 若干 4MB 分片（>4MB 才分片，或进行分片上传）
  • bucket index 池：存桶内对象列表（rgw.buckets.index）。强烈建议放在 SSD 上——桶内对象多时，list 操作全靠它
  • 多站点：通过 multisite 实现跨集群异步复制
# 关键调优
ceph config set client.rgw rgw_thread_pool_size 512        # 默认 100，高并发要调大
ceph config set client.rgw rgw_num_rados_handles 1
ceph config set client.rgw rgw_max_concurrent_requests 1024
ceph config set client.rgw rgw_obj_stripe_size 4194304     # 4MB 分片
ceph config set client.rgw rgw_bucket_index_max_aio 16
# 分片上传的单块大小（大文件上传性能关键）
ceph config set client.rgw rgw_multipart_part_size 16777216  # 16MB

# bucket index 分片（一个桶对象很多时必做）
radosgw-admin bucket reshard --bucket=my-bucket --num-shards=32

11.3 CephFS（文件存储）

唯一需要 MDS 的接口。MDS 只管元数据（目录树、文件名、权限、inode），文件数据本身仍然直接由客户端写进 RADOS——这是 CephFS 与传统 NAS 的根本区别，也是它不会遇到元数据 I/O 瓶颈的原因。

  • MDS 高可用：1 个 active + N 个 standby（standby-replay 可做热备，秒级接管）
  • 多活 MDS：把目录树分片给多个 active MDS，支撑超大目录；可配 affinity 把热目录固定到指定 MDS
  • 配额：支持目录级容量/文件数配额
  • NFS 导出：通过 NFS-Ganesha 把 CephFS 导出为 NFS
ceph fs volume create cephfs                 # 一条命令建 fs + 两个池 + MDS
ceph fs status
ceph fs get cephfs

# 多活 MDS
ceph fs set cephfs max_mds 2
# 把某个目录固定到 MDS.1
setfattr -n ceph.dir.pin -v 1 /mnt/cephfs/hot-dir

# 常用参数
ceph config set mds mds_cache_memory_limit 4GB   # MDS 缓存上限
ceph config set mds mds_bal_fragment_size_max 100000   # 目录过大时自动分片
ceph config set mds mds_max_file_recover 64

写延迟高① 查慢盘　② 查网络 RTT/P99　③ 检查 WAL 是否在快设备上别关写日志换性能（那是丢数据）

14容量规划与监控

14.1 可用容量到底怎么算

裸容量 → 可用容量 的四次扣减：

① 进制换算：厂商 1TB = 10¹²，系统 1TiB = 2⁴⁰ → 约打 0.909 折
② 冗余开销：3 副本 → ÷3（利用率 33%）；EC 4+2 → ÷1.5（利用率 67%）
③ 安全水位：不能用到 100%，要留到 85%（nearfull）→ 再乘 0.85
④ 恢复余量：坏一块盘时，重建需要备用空间 → 再预留 5~10%
# 计算示例：10 台服务器 × 12 块 8TB HDD，3 副本
裸容量      = 10 × 12 × 8 TB          = 960 TB（厂商单位）
转为 TiB    = 960 × 0.909             ≈ 873 TiB
3 副本后    = 873 / 3                 ≈ 291 TiB
85% 水位    = 291 × 0.85              ≈ 247 TiB
预留 8%     = 247 × 0.92              ≈ 227 TiB  ← 这才是你能承诺给业务的容量

# 反推：要给业务 100TiB 可用（3 副本），需要多少裸容量？
100 / 0.92 / 0.85 × 3 / 0.909 ≈ 420 TB 裸容量（约 53 块 8TB 盘）
一个反直觉的真相：3 副本集群的"利用率"只有 ~26%（0.909 × 0.333 × 0.85 × 0.92）。
这就是为什么 EC 池在冷数据场景能省一半以上的钱 —— 4+2 EC 的利用率约 52%，正好是 3 副本的两倍。
